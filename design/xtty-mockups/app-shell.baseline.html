Baseline

app shell — xtty at launch

The window macOS puts on screen when xtty starts: one tab, one pane, the session sidebar open at 220pt, the git-review panel collapsed to zero. Read from the shipped Swift at the tip of main; every structural fact below carries a file:line citation. This file is also the chrome donor — later scenarios copy its .xt-* layer rather than re-deriving the window.

The launch state, verified rather than assumed. gitReviewVisible is initialised false (TerminalWindowController.swift:85), its hosting view is created and immediately hidden (:213–215), and its width constraint is activated at constant 0 (:222). The sidebar's is activated at 220 (:220) with sidebarVisible = true (:75). So at launch the terminal gets all the remaining width — 680pt, not the ~400pt squeeze DESIGN.md §5 describes. That squeeze is real, but it belongs to git-review-flat, where the panel is open.

Both sidebars are painted flat, and that is deliberate. xtty authors no material anywhere — a grep for NSVisualEffectView, vibrancy, blur and shadow across App/ and XttyCore/Sources/ returns nothing. AppKit supplies one regardless: the .listStyle(.sidebar) List (SessionSidebar.swift:113) renders a live behind-window vibrancy material even inside xtty's bare NSHostingView. Active, it is roughly 18% of whatever desktop sits behind the window, saturation-boosted ~2×, over a #24252b base — so the real colour depends on the viewer's wallpaper and cannot be reproduced here. --xtty-panel-bg is that material measured over a neutral mid-grey backdrop. Inactive is the honest one: the material goes fully opaque at exactly --xtty-panel-bg-inactive, backdrop-invariant.

No backdrop-filter is used, and none should be. A mockup's backdrop is this page, not the user's desktop — a blur here would sample the wrong thing and present the result as measured.
The caret differs between the two variants, and that is sourced, not stylistic. SwiftTerm's caret draws a filled block when hasFocus is true and a 3pt hollow stroke when it is not (CaretView.swift:24–40). hasFocus is _hasFocus && (window?.isKeyWindow ?? true) (MacTerminalView.swift:708–712) — it folds in window-key state, not just first-responder state. So an inactive xtty window shows a hollow caret even though its pane is still the first responder. DESIGN.md §4 records the filled/hollow rule under Splits but does not mention that window activation triggers it too.

Chrome specimen — the native tab bar

A single-tab xtty window shows no tab bar, so the two variants above have none. tabbingMode = .preferred and a shared tabbingIdentifier (TerminalWindowController.swift:145–146) tell macOS to group xtty windows as tabs; they do not make the bar appear. macOS shows it once a second tab joins the group — addTabbedWindow, XttyApp.swift:296 — or when the user picks View ▸ Show Tab Bar. The window controller reads the same truth back as window.tabbedWindows?.count ?? 1 (:785, a DEBUG-only harness dump — corroborating, not load-bearing). Drawn here as a labelled specimen so window-tabs reuses the markup (data-tabbar="true") without it contaminating the launch baseline.

Where this page cannot tell the truth

#On screenHere
H1The sidebar is a live vibrancy material sampling the user's desktop.A flat measured stand-in. No backdrop-filter, on purpose — see the note above the citations.
H2SF Symbols (chevron.right, checkmark.circle.fill) drawn by CoreText at the system's optical weights.Hand-drawn inline SVG at the cited sizes. The proportions are approximations; the sizes and colours are not.
H3SF Mono at 13pt; cell width and height come from CTFont metrics.SF Mono is unavailable to a browser, so the stack falls back to ui-monospace/Menlo. Column counts and line breaks in the grid above are approximate and will not match the app cell-for-cell.
H4Traffic lights are AppKit-drawn, with hover glyphs and a per-OS gradient.Three flat circles at quarantined sizes.
H5The tab bar is drawn by macOS, including its selected-tab shape, drag affordances and overflow.A rectangular approximation in a clearly labelled specimen, not in either variant.
H6macOS composites a drop shadow outside the window's bounds.Omitted. --elev-raised is none and xtty draws zero shadows; adding one would read as an xtty decision.
H7SwiftUI's .listStyle(.sidebar) applies its own header treatment, row hover, and focus ring.Only the cited font, weight and colour are reproduced. Header casing and hover states are AppKit's and are not drawn.
H8The window is resizable; the sidebar and git panel have content minimums (180 / 240) and collapse to zero rather than reflowing.Fixed at 900×560. Below ~950px of viewport this page scrolls horizontally rather than squeezing a window that does not squeeze in the app either.
H9Prompt text and any colour in command output belong to the user's shell and the programs they run.A stock zsh prompt and two red status letters drawn from --xtty-ansi-1. What is recorded is only that SGR n resolves to --xtty-ansi-n from the theme — not a claim about git's colour map, which is git's and outside this baseline.

Where DESIGN.md and the source disagree — the source wins

#DESIGN.md / tokens.css saysThe source says
C1 §4: “pane rows with block rows indented 18pt beneath them; inactive panes dimmed to 0.55.” tokens.css repeats it: --xtty-row-dim — “inactive-pane dimming”. Wrong subject. The 0.55 at SessionSidebar.swift:179 is .opacity(block.isActionable ? 1.0 : 0.55) on SidebarBlockRow — it dims a block row whose scroll/copy anchor is stale or trimmed out. Nothing in SessionSidebar.swift dims a pane row for being inactive. No pane row on this page is dimmed, and session-sidebar should apply 0.55 to stale block rows only.
C2 tokens.css: --text-xs: 9px /* M SessionSidebar.swift:127 (block-status caption) */. Value right, description wrong. Line 127 is .font(.system(size: 9, weight: .semibold)) on the disclosure chevron. There is no 9px block-status caption; block rows use .caption/.caption2 (10px) at :170, :187, :191. The chevron is what this page binds it to.
C3 §5: “At the default 900pt width with everything open, the terminal is squeezed to roughly 400pt — that squeeze is a real design fact worth showing.” True, but not at launch — it needs the git panel open, and gitReviewVisible = false (:85). At launch the terminal column is 680pt. The squeeze belongs to git-review-flat.
C4 tokens.css: --xtty-scroller-w: 17px, tagged P with no consumer noted. It is load-bearing: SwiftTerm reserves it on the terminal's trailing edge and subtracts it from the grid's usable width (getEffectiveWidth). Any scenario that counts columns must subtract 17 from the pane width first, whether or not the scroller can scroll.
C5 §4 records the filled/hollow caret rule under Splits, as a pane-focus cue. It is also a window-activation cue: hasFocus folds in window.isKeyWindow. That is why Variant 2's caret is hollow — the difference between the two variants is not only the sidebar fill.
C6 §1: xtty “authors no material, blur, gradient, or shadow anywhere”; §6: “Flat. Hairline separators … do all the layering work.” Confirmed for materials — and stronger than stated for separators: buildLayout (:206–243) adds three subviews and no divider view at all, so there is no hairline between the sidebar and the terminal. The only boundary is where the material stops. None is drawn here.
