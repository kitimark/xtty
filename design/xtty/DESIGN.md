# xtty

> Category: Developer Tools
> Surface: web

A native macOS terminal emulator with almost no visual identity outside the terminal grid. Stock AppKit and SwiftUI chrome, the user's own accent color, one bespoke component. The restraint is the design.

**Provenance.** Hand-authored by reading xtty's shipped Swift source at commit `3bc40c7` — `App/*.swift` and `XttyCore/Sources/XttyCore/`. Every value below is either **cited** to `path:line`, or explicitly marked **platform** (AppKit/SwiftUI resolves it; xtty sets nothing) or **derived** (xtty has no equivalent). Do not cite a platform or derived value back as an xtty design decision.

This package cannot be regenerated by any tool: Open Design's importers scan CSS/Tailwind/React-family files only and would extract nothing from a Swift tree. **Never run "Import from folder" against this directory** — that path regenerates this file from a source scan and destroys the prose. Register by symlink with `make design-link`. (The separate folder import used for the *mockups project* is a different, safe mechanism.)

## 1. Visual Theme & Atmosphere

xtty looks like it was built *by* Apple's frameworks rather than skinned on top of them: standard `NSWindow` chrome, native window tabbing, system-semantic colors, SF Symbols. The terminal grid is the hero; every panel around it recedes.

xtty **authors** no material, blur, gradient, or shadow anywhere — a grep for `NSVisualEffectView`, vibrancy, blur and shadow across `App/` and `XttyCore/Sources/` returns nothing. Two honest caveats: `.listStyle(.sidebar)` inherits whatever AppKit gives it, and the find bar is SwiftTerm's own `.popover` and is genuinely vibrant. So "xtty draws nothing fancy" is true; "no material appears on screen" is not.

There is no app icon and no `Assets.xcassets` — an open gap, not an oversight.

## 2. Color Palette & Roles

### Core palette

- **Background:** `#1d1f21` — the terminal's dark-theme canvas, the app's one authored color (`XttyConfig.swift:62`).
- **Border:** `#333537` — derived: AppKit's `separatorColor` (`rgba(255, 255, 255, 0.098)`) composited over the terminal canvas; xtty draws no border of its own.
- **Foreground:** `#c5c8c6` — terminal ink and caret, a single value (`XttyConfig.swift:61,63`).
- **Accent:** `#007aff` — **reference only.** xtty resolves `Color.accentColor` at runtime; the user's System Settings accent is the real value.

A light terminal theme also ships — white ground with `#1d1f21` ink (`XttyConfig.swift:70-72`) — and both themes share the same standard 16-color ANSI palette (`XttyConfig.swift:38-55`). Only these two themes exist; there is no custom-palette mechanism.

### Roles

Chrome text is SwiftUI `.primary` / `.secondary` only, never a fixed value. Selection is the accent at 18% (`SessionSidebar.swift:137`, `GitReviewView.swift:229`).

**Session status** (sidebar): spinner for running, secondary circle for idle, green check for done, red octagon for error, purple for blocked (`SessionSidebar.swift:250-268`).

**Git status letters** (`GitReviewView.swift:204-209`): `M` orange, `A` green, `R` blue, `!` red, `?` secondary — and `D` deliberately **muted, not red**. That last one is a design decision, not an oversight; preserve it.

Terminal content in a mockup must come from `--xtty-ansi-0` … `--xtty-ansi-15`. Never invent a color for a prompt, `ls` output, or a diff.

## 3. Typography Rules

No branded typeface, intentionally. Chrome is the system font at SwiftUI's semantic sizes; the terminal is the monospaced system font (SF Mono) at 13pt, user-overridable (`XttyConfig.swift:124`, `TerminalConfigurator.swift:19`).

Measured sizes: 9px block-status captions (`SessionSidebar.swift:127`), 11px for the glyph and diff-row workhorse, 12px in the toast (`SpatialToast.swift:16`), 24px for empty-state glyphs (`GitReviewView.swift:89`).

**The one trap:** an unmodified SwiftUI `Text` renders at default body — 13px, not 11. The sidebar's pane label (`SessionSidebar.swift:207`) has no `.font()` modifier, so it is 13px and binds `--text-xl`. `--text-base` (11px) is for glyphs and diff rows, *not* body copy. Getting this backwards makes the sidebar look uniformly too small.

SF Mono is not available to a browser; use the `--font-mono` stack and accept that cell metrics are approximate.

## 4. Component Stylings

**Window** — content 900×560 (`TerminalWindowController.swift:92`); the titlebar sits *above* that rect, so do not draw chrome inside the 560. Native macOS tabs.

**Session sidebar** — 220pt, content minimum 180pt (`TerminalWindowController.swift:68`, `SessionSidebar.swift:114`). One section per tab; pane rows with block rows indented 18pt beneath them; inactive panes dimmed to 0.55.

**Git review panel** — 280pt (`TerminalWindowController.swift:79`); the 240 in `GitReviewView.swift:30` is the SwiftUI *content minimum*, a different layer — never conflate the two. Collapses to 0, it does not reflow. Flat and tree layouts; the file list clamps to 220pt once a diff is showing (`GitReviewView.swift:131`).

**Splits** — nested with `.thin` dividers. The *only* focus cue is the caret: filled when focused, 3pt hollow when not. No border, no dimming.

**Toast** — the one bespoke component in the app: black at 78%, radius 8, white 12pt text, 250ms/350ms fades (`SpatialToast.swift:16-56`). Its radius is the only custom corner radius anywhere.

**Quake terminal** — borderless, full width, 40% of the screen's *visible frame* height (`QuickTerminalController.swift:30`). No chrome at all.

**Find bar** — **vendor-owned.** It belongs to SwiftTerm, not xtty; changing it means patching SwiftTerm. Draw it as it is, and do not propose changes to it as if it were ours.

## 5. Layout Principles

Horizontal composition is `[sidebar 220 | terminal flex | git 280→0]`. At the default 900pt width with everything open, the terminal is squeezed to roughly 400pt — that squeeze is a real design fact worth showing, not a mockup bug to avoid.

**Spacing is dense: a 2px rhythm**, not a web 8px one. Row spacing of 2, padding of 6–10 (`SessionSidebar.swift:121`, `GitReviewView.swift:40,61`). Generic web padding turns xtty into a dashboard — this is the single fastest way to make a mockup stop looking like the app.

`--section-y-*` is deliberately `0`. There are no scrolling page sections; this is a tool window.

## 6. Depth & Elevation

Flat. Hairline separators and native window chrome do all the layering work. `--elev-raised` is bound to `none` on purpose, overriding the schema's shadow default — a raised tier would be a fabrication. The only depth cue in the entire app is the toast floating over the grid, and it earns that with opacity, not a shadow.

## 7. Do's and Don'ts

**Do** inherit system semantics — `.primary`/`.secondary` for text, the accent for selection. **Do** keep the terminal dominant. **Do** cite the source for anything a baseline mockup draws.

**Don't** hardcode a brand accent; `#007aff` in the tokens is a stand-in for the user's own accent. **Don't** invent terminal content colors outside the ANSI tokens. **Don't** add shadows, gradients, materials, or letter-spacing. **Don't** loosen the 2px rhythm.

**Don't draw these at all**, even as proposals:
- **A settings pane.** xtty has no settings UI. Configuration is a file (`~/.config/xtty/config`); the App menu is About/Hide/Quit. A settings mockup describes a feature that does not exist and must say so on the page.
- **A project file-tree browser.** Rejected as off-mission IDE-creep; this is a standing decision, not an open question.
- **Any account, login, or sync chrome.** xtty is account-free by hard product requirement.
- **An app icon or launch screen.** None ships; there is nothing to reproduce.

## 8. Responsive Behavior

There are no breakpoints. This is a resizable desktop window, not a responsive page. Panels **collapse to zero width**; they do not reflow, stack, or become a drawer. The sidebar and git panel have content minimums (180 / 240) below which their contents stop making sense.

The quake terminal is the only viewport-relative surface, and it tracks the screen's *visible* frame — excluding the menu bar and Dock — so a CSS `vh` approximation runs slightly tall. Annotate that where it is used.

The `--container-gutter-tablet` and `--container-gutter-phone` tokens exist only to fill required schema slots. They are not breakpoints and mean nothing here.

## 9. Agent Prompt Guide

**Deliver HTML.** Never write, edit, or propose Swift. Mockups are hand-translated into SwiftUI by a human afterward, as separate work.

**Baseline first.** A file named `<scenario>.baseline.html` reproduces what ships *today*, and must cite the `App/*.swift:line` implementing each thing it draws. Only change a baseline to make it more faithful. Design ideas go in `<scenario>.proposal-<slug>.html` instead.

**A proposal with no baseline sibling means the feature does not exist in xtty.** Say so in the rendered page, visibly, not just in the filename.

**Never modify** `index.html` (the hand-authored gallery) or `README.md` (the project brief) — both are maintained by hand.

**If a value you need is missing from `tokens.css`, do not invent it.** Say what is missing and propose it as a new token. A silently invented value is indistinguishable from a real one once it is in the markup, which is exactly how a mockup starts lying about the app.
