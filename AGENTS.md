# AGENTS.md — xtty

Guidance for AI agents (and humans) working in this repository. This is the canonical project guide; `CLAUDE.md` symlinks to it.

## What this project is

**xtty** is a **native macOS terminal emulator**. It is greenfield and in the **build** phase: the app already launches a live terminal (the user's login shell in a SwiftTerm engine hosted in AppKit). The direction, requirements, and design are documented in `research/`; implementation proceeds milestone-by-milestone via the OpenSpec workflow.

**Learned refutations — do not re-propose.** Each was settled by measurement; details in [HISTORY.md](HISTORY.md) and the linked research docs:

- **Test retry flags / retry tolerance are banned** — retries mask the per-launch race class (a retried VM run green-lit two genuinely broken tests).
- **`run_in_background` strands subagents** — its "re-invokes you" promise is false for them; a subagent that ends its turn mid-work is never resumed. Foreground bounded waits only.
- **Re-asserting `NSApp.mainMenu` is a no-op** — SwiftUI's reconciler mutates the same `NSMenu` instance in place; the shipped fix dropped the SwiftUI lifecycle (`NSApplicationMain`).
- **`hasForegroundJob`-based readiness waits are refuted** — fg==shellPid from ~3 ms; 15–57 ms child bursts invisible to the 150 ms dump sampler; use the computed-marker execution roundtrip.
- **SwiftUI `NSViewRepresentable` hosting renders SwiftTerm black** on macOS 26 — host the terminal view in an AppKit `NSWindow`.
- **The Metal renderer was rejected by measurement** (worse p99 tail, more memory, no median win); resurrecting it requires re-running the archived P7b methodology, not an opinion.
- **The Scope-B project file-tree browser is rejected** as off-mission IDE-creep (P6b addendum in `p6-file-diff-decisions.md`).
- **`launchEnvironment`/CI env vars are stripped by the curated child-env seed wall** — environment fixes must land at the product seam (`ShellResolver`) or they silently no-op.
- **Agent-definition edits reach spawns with unpredictable lag** — verify delivery per run (the `Definition:` stamp); a spawn 63 s post-edit was served the stale copy.
- **Guest bash 3.2 has no bracketed paste** — the VM rig's multi-line-paste red is a benign rig residual, not a product bug.
- **The hosted-runner find-bar wrap is not reproducible from the image build** — stock macOS `PS1='\h:\W \u\$ '` is byte-identical on runner + VM (`runner-images` sets no `PS1`); the runner's ~61-char `\h` is GitHub-network-injected at *runtime* (the image sets only `Mac-<epoch>.local`), so the sole reproduction lever is hostname *length*, which we control — and the short-`\h` Tart VM is blind to prompt-width flakes by construction (`ci-runner-prompt-width-forensics.md`).
- **`xcrun -f metal` inside a VM is a false positive** — it PATH-resolves while the toolchain is unfetchable in-guest.
- **The macOS Local Network gate cannot be granted or neutralized at build time** — not TCC (LN is not a TCC service; the DB has no `kTCCServiceLocalNetwork`), not TN3179's `defaults write Allowed*LocalNetworkAddresses` (a *destination-address* exemption, orthogonal to xtty's reverse-DNS *query* trigger — refuted baked-in too), not an NE-store pre-seed (`nesessionmanager` prunes records lacking live-consent provenance on every boot; only an explicit user *Allow* both persists and silences), not the SSH/CLI-child auto-grant (a GUI app bundle is its own responsible code). The durable fix removes the trigger: `PaneController.localHostNames` from `gethostname()` (matches the shell's `$HOST`, behavior-preserving + more correct) — or run the shell-dependent suite **headless** (`local-network-privacy-forensics.md` §8). **(2026-07-08: the removal-of-trigger fix landed & archived as `fix-osc7-hostname-reverse-dns` — the `gethostname()` swap, measured GREEN by effect: 0/0/0 on a fresh graphics zsh rig; §9.)**
- **Don't pre-build a speculative dev-workflow agent roster** — add an `xtty-*` agent only after its friction recurs across several changes and is provably under-done (both existing agents were reactive; a proposed roster-of-4 was refuted by the dev-workflow forensics → build one **change-set-aware** `openspec-critic` first, adopt fork-per-change authoring as a habit). Delegate only above the ~12k-token subagent-inheritance floor; compute cross-artifact state on demand, never cache counts (`dev-workflow-agent-orchestration.md`).
- **A rule that lives only in AGENTS.md doesn't reach the `/opsx:apply` loop** — the generic apply skill walks `tasks.md` checkboxes, models only *implement* tasks, and never re-reads AGENTS.md; `config.yaml` `rules` don't ride `openspec instructions apply` either. So any *recurring apply-time procedure* must be written at the **point-of-tick** — a marker in the task line (this is why the three delegations **and** the archive ritual all carry a `⟶` marker; measured: the `fix-osc7` archive, with no marker, improvised `openspec archive` and stalled until the user intervened). The archive marker (`⟶ archive-ritual`) must anchor to the **hand-authored committed** procedure in this file, never to the CLI-generated `/openspec-archive-change` skill — even though that skill is now tracked too, `openspec init`/`update` can rewrite it on a version bump, so the hand-authored procedure (whose text is under our control) is the stable anchor a committed task can depend on. Guideline **G13**, `archive-trigger-affordance-forensics.md`.
- **Don't skip-and-partition the shell-dependent XCUITests (per-shell `.xctestplan`s + honest `XCTSkip`) — parameterize-and-assert instead.** A skip is a coverage hole (it verifies nothing on that shell) and the two-`.xctestplan` partition adds machinery + XcodeGen-fidelity risk; since the shell behaviors are *measured*, each shell-dependent test should assert the **correct behavior for the terminal's observed capability** (`bracketedPasteMode` / capture-active), keeping a skip only as a last resort. Settled by `split-shell-dependent-testplan` (the original skip-and-partition sketch was pivoted at explore, then measured **`41/0/1` on both goldens with 0 vacuous passes** and **0 last-resort skips** — the partition was dropped, never introduced). `research/03-analysis/shell-dependent-test-partitioning.md`.
- **A `$0` local `make install` needs no DMG / notarization / Homebrew ceremony — those are download-channel-only.** A locally-compiled app never receives `com.apple.quarantine` (verified 2026-07-08 on xtty's own Debug **and** Release builds), so an ad-hoc (or `xtty-dev`-signed) Release copied to `/Applications` launches clean past Gatekeeper — DMG/notarization/cask matter only for a *downloaded* artifact (the deferred `$99` `add-distribution-signing`/`add-homebrew-distribution`). The install target = build `-configuration Release` → `ditto` to `/Applications`, version stamped via a CLI `MARKETING_VERSION=…` override (proven to reach the synthesized `Info.plist`), plist fields kept numeric (the `git describe --tags --always` draft was refuted — `--always` defeats the `|| echo` floor). Guideline G14; `research/03-analysis/local-install-workflow-research.md`. **(2026-07-08: shipped & archived as `add-install-workflow` — `make install`/`make restart` + the `v0.0.1` tag; measured `Signature=adhoc`, `CFBundleShortVersionString=0.0.1`/`CFBundleVersion=256` numeric, empty `com.apple.quarantine`, install survives `make clean`.)**
- **A raw `CGEvent` HID scroll is silently dropped by the XCUITest runner — drive wheel gestures through XCUITest's automation channel, not `.cghidEventTap`.** The `xttyUITests-Runner` has no Post-Event/Accessibility grant (`CGPreflightPostEventAccess=false`, Codex-rescue-confirmed), so a `CGEvent(scrollWheelEvent2Source:…)` posted to `.cghidEventTap` never lands (and `CGWarpMouseCursorPosition` moves the cursor *sprite* but doesn't update the WindowServer's window-under-cursor, so even a pixel-correct raw scroll misroutes — proven by a coord read-back that matched the target yet routed nowhere). Use `XCUIElement.scroll(byDeltaX:deltaY:)` (element-targeted, cursor-independent) for the gesture and wrap it in `XCUIElement.perform(withKeyModifiers: .shift) { … }` for a Shift-modified wheel — a held-Shift CGEvent keyDown is **not** picked up by the automation-synthesized scroll (flags=0). Sign: XCUITest `scroll` positive `deltaY` = wheel-**up** (button 64); a `CGEvent` `wheel1` sign is the *inverse*. Settled landing `fix-scroll-wheel-mouse-reporting` (`AppUITests/XttyMouseWheelUITests.swift`); peekaboo (an external, granted process) *can* post the raw scroll, which is why the manual verify-by-effect worked where the runner's raw post did not.
- **zsh's line editor (ZLE) turns application-cursor mode (DECCKM/`smkx`) ON at every prompt** — so a bare **zsh** prompt reports SS3 `ESC O A/B` cursor keys while a bare **bash** prompt reports CSI `ESC [ A/B`. A DECCKM-dependent test must **not** assume "normal at a bare prompt" (bash-only). Hold a known DECCKM state deterministically across both goldens by keeping the shell busy in a foreground command (`printf '…'; sleep N`) so ZLE can't re-toggle `smkx`/`rmkx` between the setup and the gesture. Settled by `fix-scroll-wheel-mouse-reporting`'s two DECCKM cursor-key XCUITests (normal + application arms, green on both goldens).
- **Don't drop momentum, cap-and-discard scroll distance, or time-throttle the wheel** — a blanket `momentumPhase` guard stops trackpad/Magic-Mouse scrolling dead the instant fingers lift (no native inertial coast), and a fixed per-gesture emission cap that subtracts the full accumulated delta while emitting only the cap silently discards travel on fast flicks. Bound flood by **whole-cell quantization** instead (accumulate a losslessly-carried sub-cell remainder, emit ~1 report/key per whole cell traversed, reset the remainder on each new gesture's `.began` phase) — the mechanism all 5 surveyed mature peers (iTerm2, Ghostty, kitty, WezTerm, Alacritty) use; none drop momentum or cap-and-discard. Settled by `smooth-scroll-wheel-momentum` (measured by-effect on a physical trackpad: coast continues after finger-lift, no lost distance on a fast flick, htop stays interactive through the coast); `research/03-analysis/scroll-momentum-smoothness-research.md`.

- **A model-authored artifact can never gate archive — the human is the gate, not the model.** The first shape of `add-cross-model-design-review` was a **self-policing** automated gate: a model ran the cross-model review, wrote a "converged" `cross-review-receipt.md`, and archive mechanically checked that receipt. Six rounds of the change's own cross-model review refuted it — **every receipt/verdict/coverage-label is model-authored**, so a mechanical check of one still trusts the model, and a model could dismiss every finding and self-certify **by doing its assigned job** (the deep flaw: *correct* behavior defeats the guarantee). Deleted with it: the `OpenSpec-Change:` per-commit ownership trailer + commit-hash manifests (the change could not even dogfood its own trailer rule on its already-landed history), convergence-verdict-as-eligibility, the 3-way degradation classifier's hard-fail/auto-satisfy arms, and coverage-label-as-gate-input. **The shipped shape splits authority from helpfulness:** *the worker may be arbitrarily helpful but carries zero authority; the gate is authority-complete, has near-zero machinery, and reads no model-authored artifact* — eligibility is a **human attestation** (the reviewed-state digest recorded on a delimited line in `tasks.md`), checked against git by committed deterministic tooling. **Confirmed by effect at the 2026-07-12 self-dogfood:** the gate failed closed on a bare tick (no digest recorded), on an uncommitted attestation (an attestation must bind a *committed* state), and on a stale/rewritten/deleted attestation — going green only on a genuine human attestation; and the model, asked three times to write the attestation line itself, correctly **refused** (had it complied, the resulting green would have certified the opposite of what it claims). `research/03-analysis/cross-model-design-review-axes.md`.
- **Don't harden a mechanical gate against the model that runs it — and don't "iterate cross-model review until both models agree."** An in-session convergence experiment ran `add-cross-model-design-review`'s own cross-model loop *on the proposal* (Fable-5 fixing, `gpt-5.6-sol` adversarial-verifying, Claude adjudicating; Workflow `wf_454a4338-7e8`): over 4 **bounded** rounds it **did not converge** — each mechanical hardening of the review-base/range provenance opened the next git-manipulation narrowing (recorded-base → pre-attestation rewrite → check-5 re-record deadlock → ownership≠completeness → range-completeness → directory-rename rename-blindness), the spec bloated **+45%**, round 4 regressed a round-1 guarantee. The adversary is *the model running the tool* — it controls git history, so the closable-bypass set is **unbounded** and every member reduces to the single accepted **R3** residual (a repo-controlling model performing a forbidden act — the trust class already accepted for every committed procedure). *"Delete every mechanically-closable class"* is the trap (infinite regress); adversarial review never returns zero, so *"until both models agree"* has no fixed point (operationalize convergence instead as *no open actionable beyond documented-accepted residuals*, bounded). **Fix = thin the *claim*:** mechanical checks are **accident tripwires + human-legibility aids**, not airtight guarantees; adversarial resistance = the human reading the ledger + R3. **And: dev tooling is validated by building + using it (the real dogfood), not by adversarial spec-review — which has a hard diminishing-returns cliff (~2–3 useful rounds, then bloat/regression). (2026-07-12 confirm §9 — the *corrected* loop, thin claim + a content-measured floor, re-run as a proactive co-draft, converged in 1 round / 0 net bytes, `wf_15f6ecb9-aad`; the floor must measure content — words/bytes — not lines: a line-neutral edit still grew +253 bytes, caught only by an independent `wc -lwc` recompute → G-TARPIT-5.)** `research/03-analysis/cross-model-review-tar-pit-forensics.md`; guidelines G-TARPIT-1..5.

The fix (**A'**, `brief-cross-review-pass-b`, archived 2026-07-13) passes a brief — design intent + claims-to-soundness-check + drill digest — as the trailing positional on the existing `adversarial-review` call: **additive** (check these **and** report anything outside them), **advisory** (zero gate force), **staged out-of-repo and read into one positional** (`mktemp` → `"$(cat)"`) so a brief carrying backticks/`$`/newlines isn't shell-expanded, word-split, or `join(' ')`-collapsed. `task --write` drilling was **rejected** (loses the server-enforced schema, adds a write-safety surface with default cwd = repo root, and OpenAI's content-filter aborts security-flavoured drills). **Dogfooded on itself through the full human-attestation gate (archived 2026-07-13):** the briefed pass engaged the design's specific claims, its consensus-suppression guard **correctly refused** a shared-framing B∧C agreement (resolving open-question R2-1 by usage), and — reviewing itself — it caught the one real delivery-layer defect the design had missed (the shell-quoting gap), fixed in-run and proven by effect (a clean instance of **G-TARPIT-4**: validate dev tooling by building + using, not by another spec-review round). `research/03-analysis/codex-review-integration-forensics.md`.

## Building

The Xcode project is generated from a committed `project.yml` via **XcodeGen**; the resulting `xtty.xcodeproj` is **gitignored** (never commit it).

**Quick start — use the `Makefile`.** It is the single entry point; run `make` (no target) to list everything. It only wraps the commands documented below.

| Command | What it does |
| --- | --- |
| `make doctor` | check the prerequisites you must install yourself (XcodeGen, full Xcode) and print how to get each |
| `make setup` | first-time, post-clone: `doctor` → bootstrap SwiftTerm → generate the project |
| `make build` / `make run` | build (then launch) the app — **auto-bootstraps SwiftTerm and regenerates the project only when their tracked inputs changed** |
| `make install` / `make restart` | install a stable, version-stamped **Release** build into `/Applications` (a self-contained copy) / quit + relaunch the installed app |
| `make test-core` | the fast `XttyCore` unit loop (no app build) |
| `make test` | the app XCUITests (the benchmark e2e is opt-in — set `XTTY_RUN_BENCH_E2E=1` — so routine runs never prompt for Screen Recording) |
| `make bench` | the P7a performance harness — latency + per-scenario memory → a JSON report under `build/bench/` (latency is **coarse/experimental**; memory is the trustworthy result — see `research/03-analysis/p7-measurement-methodology.md`) |
| `make image` | build the minimal **~40 GB local test-VM image** (Packer + Tart, from pinned inputs) — prereqs are human-gated and only advised (packer install + a one-time Apple-ID Xcode-`.xip` download); see `packer/README.md` |
| `make bootstrap` / `make generate` | force a re-run after editing the SwiftTerm pin/patch or `project.yml` |
| `make clean` / `make reset` | remove build outputs / nuke + rebuild the SwiftTerm checkout |

The targets are thin wrappers — reach for the underlying commands below directly if you're not using `make`, or to understand what a target does:

- **Prerequisite:** XcodeGen — `brew install xcodegen` (developed against **v2.45.4**). Building/testing the app target needs **full Xcode** (the Command Line Tools alone lack `xcodebuild`, `XCTest`, and swift-testing). Verified against **Xcode 26.6**.
- **SwiftTerm checkout (one-time, P4b-2):** SwiftTerm is consumed as a **gitignored upstream clone** at `external/SwiftTerm`, pinned via `patches/swiftterm/UPSTREAM_CONFIG.sh` (currently `v1.13.0`) with a tracked **patch** applied (the P4b-2 accessors add + a `Package.swift` hunk stripping the Metal shader resource, so builds need **no Metal toolchain** — `retire-metal-renderer`) — the no-fork "patch in repo" mechanism, Playwright-style (see `research/03-analysis/swiftterm-fork-vs-patch-strategy.md`). After cloning xtty, run **`scripts/bootstrap-swiftterm.sh`** — it clones `external/SwiftTerm`, restores the pinned ref pristine (checkout + reset + clean, enforced every run), and `git apply`s `patches/swiftterm/xtty-accessors.diff`. Re-run it after editing the pin or the patch. The build fails to resolve `../external/SwiftTerm` until this runs. Nothing under `external/SwiftTerm` is tracked (it's `.gitignore`d build infra); only the pin + the `.diff` + the script are version-controlled. Retire the whole mechanism once the accessors land in an upstream SwiftTerm release.
- **Local VM test image (optional):** `make image` builds the minimal **~40 GB** Tart image `xtty-test:26.5` from pinned inputs (no simulators, no Metal toolchain, no xtty source baked in; prereqs human-gated — packer + a one-time Apple-ID Xcode `.xip` download). Purpose: CI-parity XCUITest runs — the per-launch race class reproduces at 3 vCPU in a VM, not on bare metal. Runtime workflow, acceptance envelope, and expected-difference matrix: **`packer/README.md`**. Depends on `retire-metal-renderer`.
- **Generate the project:** `xcodegen generate` (re-run after editing `project.yml` or adding/removing source files).
- **Build & run:** open `xtty.xcodeproj` in Xcode, or `xcodebuild -project xtty.xcodeproj -scheme xtty build`.
- **Core package:** `XttyCore` is a local SPM package (the engine-facing seam). It builds/tests standalone from `XttyCore/` via `swift build` / `swift test` (tests need Xcode's toolchain for XCTest).
- **Install a stable build (`make install`):** builds the optimized **Release** config (git-version-stamped: short version from the latest `v*` tag with a `project.yml` floor, build number = commit count) and `ditto`-copies a self-contained `xtty.app` into `/Applications` (override with `INSTALL_DIR=~/Applications`; the previous bundle is backed up to `xtty.app.bak`). A copy — it survives `make clean`. Reuses the existing signing posture (ad-hoc default; `XTTY_SIGN_IDENTITY=xtty-dev make install` for stable code identity so TCC grants persist). **$0, no notarization, no Apple account** — a locally-compiled app is never quarantined, so it launches clean past Gatekeeper. `make restart` quits the running instance and relaunches. Debug `make run`/`make build`/`make test`/`make bench` are unchanged (the iteration path). DMG/notarization/Homebrew remain the deferred `$99` download-channel concern (`research/03-analysis/local-install-workflow-research.md`).

Signing posture (P0): **App Sandbox OFF** (`App/xtty.entitlements`), **Sign to Run Locally** (ad-hoc identity), Hardened Runtime/notarization deferred.

- **Optional stable local signing (dev convenience):** ad-hoc signing changes the app's code identity every rebuild, so TCC grants (notably Screen Recording for `make bench`) re-prompt per build. Create the self-signed cert once with `scripts/create-signing-cert.sh` (→ `xtty-dev`) and build with `XTTY_SIGN_IDENTITY=xtty-dev make build|test|bench`; unset, builds stay ad-hoc/portable. Full distribution (Developer ID + Hardened Runtime + notarization) is researched **green but gated on the ~$99/yr Apple Developer Program decision** — `research/03-analysis/distribution-signing-research.md`.

### Continuous integration (GitHub Actions)

CI runs on every push and pull request via `.github/workflows/` — **$0 and secret-free** (the ad-hoc default needs no Apple credentials; standard `macos-26` runners are free + unlimited on public repos). Two jobs in `ci.yml`:

- **`test-core`** (the **required gate**) — reconstitutes SwiftTerm and runs the fast view-free `XttyCore` unit tests (`swift test`, no app build). Deterministic; this is the check to require in branch protection.
- **`build-and-test`** (**non-blocking**) — `xcodegen generate` + `xcodebuild test` (the app XCUITests), retry-tolerant, uploads the `.xcresult` on failure. Kept out of required checks while hosted-runner XCUITest reliability is being proven.

Both jobs cache the reconstituted `external/SwiftTerm` (keyed on the pin + patch); no Metal-toolchain guard is needed — the build is Metal-free (`retire-metal-renderer`). `pr-lint.yml` enforces Conventional Commit **PR titles** (pull requests only). The workflows call `scripts/bootstrap-swiftterm.sh` directly (not `make`). Release/notarization are **not** in CI (deferred). Current CI truth: `test-core` is green and gate-worthy; `build-and-test` is non-blocking with the menu-clobber fix confirmed on CI and 2 residual rig fragilities (find-bar marker-wrap on the runner's ~72-char prompt; multi-line paste on bash-3.2) deferred to a harness-truthing successor. The full CI investigation record — runner forensics, the SwiftUI menu-clobber root cause and fix, the shell/banner fixes, per-run counts (§9–§18) — lives in `research/03-analysis/github-actions-ci-cd.md`, with the chronological digest in [HISTORY.md](HISTORY.md).

## Product values (hard requirements)

## How to work here

- **Implementation follows the phased plan** in `research/04-design/02-milestones.md` (P0 skeleton → P5 daily-driver → **P7 OSC capture (keystone)** → P8 sidebar → P10 polish). P8/P9 depend on P7.
- **Use OpenSpec for non-trivial changes** (see the OpenSpec workflow section below). The project `context` in `openspec/config.yaml` is shown to the AI on every artifact.
- **Research is background, not spec.** `research/` records *why*; `openspec/specs/` will record *what is true*. When they conflict once code exists, specs win.
- **Write up research in `research/` when it's done.** Whenever an investigation or spike produces durable findings — a tooling landscape, a comparison, an internals discovery, a dead end worth remembering — capture it as a `research/` doc *as soon as it settles* (even mid-build), in the right subfolder (`03-analysis/` for analysis, `02-internals/` for internals, `04-design/` for build-plan shifts). Follow the research-doc conventions (Provenance + Sources + ✅/❌/❓) and add it to `research/README.md`. **Capture depth — settle the *mechanism*, not just the conclusion (scaled to the finding).** Any capture with **measured claims or retired theories** carries: (1) the **mechanism/internals** (how the system actually works, with the evidence); (2) **reproducible probes** — the exact commands, what each proves *and cannot prove*, including instruments that did **not** work; (3) the **investigation record** — each retired theory as a ❌ *next to the experiment that killed it* (a fates table), so stale claims can't be cited and theories don't respawn; (4) **re-verify by effect** — how a future reader re-checks the headline claim (never a syntax/read-back check); (5) when the finding generalizes, a distilled **reusable guideline** (numbered); (6) pointers to the **evidence artifacts**. Lightweight captures (a landscape/comparison with no measurements) skip these. Exemplar: `research/03-analysis/local-network-privacy-forensics.md`. Keep the *why/landscape* in `research/`; the actionable *decision* belongs in the OpenSpec change.
- **Keep progress current when implementation lands — and keep it lean.** When a change (or a milestone's tasks) is done, update the trackers in the same session: tick the `tasks.md` checkboxes; update the change's **row in the Current-status table** (bounded: state + one-liner + detail pointer — **never a narrative paragraph**); refresh the **snapshot block** if counts/envelope/milestone position moved; **append the full narrative to [HISTORY.md](HISTORY.md)** under a dated heading in the matching section; and advance the milestone state in `research/04-design/02-milestones.md`. If the change settled a refutation worth never re-litigating, add a one-liner (with its conclusion) to the **Learned refutations** list. **Then verify against disk** — `openspec list` (active changes must match the open-changes table), `ls openspec/changes/archive/` (archived changes must be marked archived, not "pending archive"), `ls openspec/specs/` (established specs must match the list above) — and fix any tracker that disagrees with reality. Don't leave finished work looking pending or stale. The **`/xtty:capture-research`** command + **`xtty-capture-research`** skill walk this whole capture-and-reconcile checklist (place + index the research doc → reconcile the trackers → verify-against-disk). **The standard change tail — drive completion from a point-of-tick marker.** Archive + reconcile is the one recurring apply-loop procedure that lives only in this file, so it drifts out of reach of the generic `/opsx:apply` loop (measured on the `fix-osc7-hostname-reverse-dns` archive: the completion task folded archive into an implicit "on completion" clause with no procedure pointer, so the loop improvised `openspec archive` and never reached the archive skill the user expected). Give every change the same recognizable tail so the ritual reaches the checkbox-walker: (1) a **pre-archive coherence** task marked `⟶ xtty-openspec-critic (<change>)`, then (2) an **archive + reconcile** task carrying `⟶ archive-ritual`. `⟶ archive-ritual` resolves to the **committed hand-authored** procedure — the OpenSpec workflow's *"After archiving, finish the merge by hand"* + this *Keep progress current* rule + the `openspec archive` CLI — **not** to the openspec-generated `/openspec-archive-change` skill (that skill is now tracked too, but it is CLI-generated — `openspec init`/`update` can rewrite it on a version bump — so it stays an **optional accelerator**, never the stable anchor a committed task depends on). Unlike the three delegation markers, `⟶ archive-ritual` is a **procedure pointer, not an agent delegation** — the ritual runs inline and produces the very tracker edits the session must own, so there is nothing to delegate and `xtty-openspec-critic` does **not** expect an agent for it. **Pre-tick self-check:** before ticking the archive task, confirm the spec deltas merged into `openspec/specs/`, the trackers reconciled (row + snapshot + HISTORY + milestone + refutations), and verify-against-disk ran.

Its Pass C soundness reviewer runs **inline**, not as a standing agent (anti-roster). Full protocol + the human-attestation archive gate: *Cross-model design review + the human-attestation archive gate* (under OpenSpec workflow).

## OpenSpec workflow

We do **spec-driven development**: formalize *what* changes as reviewable artifacts, approve, then implement. Don't write feature code straight from a chat prompt — capture it as a change first.

**The loop** (one change per milestone from `research/04-design/02-milestones.md`):

```
explore ──▶ propose ──▶ apply ──▶ archive
(think)    (artifacts) (implement) (merge into specs/)
```

**Slash commands** (preferred entry points):
- `/opsx:explore <topic>` — thinking/investigation mode. **Never implements**; may read code/clone OSS to `/tmp` for understanding and may create OpenSpec artifacts. Use it before committing to an approach.
- `/opsx:propose <name>` — create a change and generate all artifacts (`proposal.md` → `design.md` + `specs/` → `tasks.md`).
- `/opsx:apply` — implement a proposed change by walking its `tasks.md` checkboxes. This is where real code gets written.

**Underlying CLI** (`openspec`, v1.4.x):
- `openspec list` — active changes · `openspec list --specs` — established specs
- `openspec new change "<name>"` — scaffold a change
- `openspec status --change "<name>" [--json]` — artifact build order & paths
- `openspec instructions <artifact> --change "<name>" --json` — template + rules for an artifact (follow these; do NOT copy the `context`/`rules` blocks into the file)
- `openspec validate "<name>"` — validate before committing
- `openspec archive "<name>"` — on completion, merge spec deltas into `openspec/specs/`

**Artifact order & dependencies:** `proposal` → (`design` + `specs`) → `tasks`. `tasks` is the apply gate.

**Spec delta format** (in `changes/<name>/specs/<capability>/spec.md`):
- Use `## ADDED Requirements` / `## MODIFIED Requirements` / `## REMOVED Requirements`.
- `### Requirement: <name>` with **SHALL/MUST** (avoid should/may); every requirement needs ≥1 scenario.
- `#### Scenario: <name>` with **WHEN/THEN** — scenarios MUST use exactly **4 hashtags** (3 fails silently).

**Keeping a change coherent — what to update when a requirement changes.** The four artifacts are a dependency chain (`proposal → design + specs → tasks`), so a requirement edit rarely lives alone. When you add/modify/remove a requirement in `changes/<name>/specs/`, walk this list, then run `openspec validate "<name>"` (it catches missing deltas/scenarios):
- **`proposal.md` → Capabilities** is the contract with `specs/`: every capability a spec delta touches MUST appear under **New** or **Modified Capabilities** (and vice-versa — no orphan spec dir, no listed-but-absent capability). Refresh **What Changes** / **Impact** if scope moved.
- **`specs/<capability>/spec.md`** — keep requirements **mechanism-neutral (the *what*)**; the *how* (fork vs seam, file/type names, concrete APIs) belongs in `design.md`, never inside a requirement. A **MODIFIED** requirement MUST paste the **entire** existing block from `openspec/specs/<capability>/spec.md` and edit it (partial content silently loses detail at archive). A behavioral change usually spans **multiple capabilities** — e.g. a new keybind action also touches `terminal-keybindings`; a new config key touches `terminal-configuration`.
- **`verification-harness` (almost always, in this repo)** — the custom-drawn view exposes nothing to accessibility, so any **new observable behavior** needs *both* a `verification-harness` spec delta (a new DEBUG state-dump field/observation + an e2e scenario) **and** a harness task. 25 of the 52 archived changes carried a harness delta for exactly this reason — if the harness can't see it, it isn't done.
- **Test precision vs. the claim (design-time, Decisions).** When a change adds or modifies a test, `design.md`'s Decisions (or Risks/Trade-offs) MUST state (1) the exact claim the test proves, (2) the layer/mechanism that claim lives in, and (3) why the chosen driver reaches that layer. Then match the test's depth to the claim — symmetrically: an over-deep test is as wrong as a too-shallow one, and this is not a "prefer synthetic/low-level tests" rule. Decide by where the claim lives. A real end-to-end program is the right tool for a claim that lives upstream of any program-specific behavior — e.g. `testWheelScrollsRealMouseTrackingPager` drives real `less --mouse` to prove wheel routing (whether a mouse report reaches the program at all, decided before any redraw), so the program's own escape idiom is irrelevant and the real program is exactly right. A direct/synthetic driver is the right tool for a claim about one narrow internal code path a given program may or may not exercise — e.g. in `fix-scroll-reversal-redraw-corruption` only htop's ncurses hardware-scroll optimizer hits the buggy `cmdScrollDown` (`vim` uses already-guarded `IL`/`DL`, `less` a bare `RI` with no scroll region), so a real-pager test would pass green while proving nothing; the fix is instead proven by driving the exact `SU`/`SD`-inside-a-scroll-region sequence directly via `printf`. The trap runs both directions: a driver — real program or synthetic — can silently fail to exercise the intended mechanism because the escape-idiom choice (a real program's, or your own hand-written sequence's) may not match the path under test, and a program's idiom is outside this project's control. Worked exemplars already living in Decisions/Risks (no new machinery): `split-shell-dependent-testplan` D2 (assert forwarding fidelity per the shell's observed capability), `fix-scroll-wheel-mouse-reporting` Risks (assert the deterministic routing state-dump field, not a program's own scroll count).
- **`design.md`** — re-check that decisions and requirements still justify each other *both ways*: a changed decision can leave a requirement over-/under-specified (neutralize it — e.g. drop a hard-coded mechanism), and a new requirement may need a decision plus a Risks / Migration / Open-Questions update.
- **`tasks.md`** — every requirement needs build **and** verify tasks; add or re-order them when requirements change (and split deferred work into its own task group rather than blurring scope). Any verify task that runs the **Tier-1 XCUITest suite (`make test`), a VM tier, or a full acceptance matrix** MUST carry the delegation marker `⟶ xtty-test-validator (<tier/scope>)` (see the test-validation rule in *How to work here* for the inline-vs-delegate boundary); cheap checks stay unmarked. A change's **completion** MUST carry an explicit **archive + reconcile** task marked `⟶ archive-ritual` (the *standard change tail* — placed after its pre-archive `⟶ xtty-openspec-critic (<change>)` coherence task), so `/opsx:propose` emits it and `xtty-openspec-critic` flags its absence; that marker points to the **committed hand-authored** archive ritual (see *Keep progress current*), not the CLI-generated archive skill (tracked now, but regenerable by `openspec init`/`update`).
- **`research/`** — the *why* stays in `research/` (update the relevant doc **and** its `research/README.md` line when a decision/finding shifts); the actionable *decision* stays in the change. Trackers (AGENTS **Current status**, the milestone state) are updated on completion per **Keep progress current**.

**Lifecycle rule:** `openspec/specs/` is the source of truth and only grows via `openspec archive` after a change is implemented. In-flight work lives in `openspec/changes/<name>/`. Commit proposal artifacts as `docs(openspec): …`; commit the implementation under the relevant `feat`/`chore` scope.

**Before archiving an in-scope change, run the cross-model gate's step-0 fail-closed precondition first** (see *Cross-model design review + the human-attestation archive gate* below) — it is the first act of the `⟶ archive-ritual` for any change the mechanical scope classifier deems in scope, and it gates the `openspec archive` that follows.

**After archiving, finish the merge by hand:** `openspec archive` merges spec deltas mechanically, so check the result before committing — (1) fill in the `## Purpose` of any **newly-created** spec (archive stubs it with `TBD - … Update Purpose after archive.`); (2) make the merged requirement text reflect *what actually shipped*, not what the proposal guessed (specs record what is true — e.g. correct the delta if the implementation diverged); (3) `openspec validate --all --type spec` and skim the diff for collapsed blank lines. Then commit as `docs(openspec): archive …`.

### Cross-model design review + the human-attestation archive gate

For a change **in scope** (by the mechanical classifier below), a single-model coherence pass is insufficient — pair it with a **cross-model soundness** review and a **human gate** on archive. Two layers with a hard rule between them: **the worker is arbitrarily helpful but carries zero authority; the gate is authority-complete but has near-zero machinery and reads no model-authored artifact.** (Settled after six rounds of this change's own cross-model review refuted a self-policing model-authored gate — see the Learned-refutations bullet + `research/03-analysis/cross-model-review-tar-pit-forensics.md` and `cross-model-design-review-axes.md`.)

- **Mechanical scope classifier (never a model judgment) — and it scopes the RANGE, not the change.** `scripts/cross-review-scope.sh <change>` classifies from **every path in the change's reviewed range** (`parent(<proposal.md commit>)..HEAD` — **repo-wide**, *not* the change's own paths) against a **fixed allowlist of docs/tracker surfaces** (`openspec/changes/**`, `research/**`, `AGENTS.md`/`CLAUDE.md`/`HISTORY.md`/`README.md`, `packer/README.md`): any path **outside** ⇒ **in scope** (exit 10); an **unrecognized/ambiguous** path ⇒ **in scope, fail-closed**; every path inside ⇒ **out of scope** (exit 0 — the single-agent `/xtty:review` suffices); a range it cannot resolve ⇒ **refuse** (exit 2). The script is the authority on the exact patterns; the allowlist errs narrow (over-inclusion costs one review, under-inclusion is a bypass). **⚠️ Read the verdict honestly — it is *non-attributive* and it *latches*:** an in-scope verdict says only that **some** path in the range is out-of-allowlist, **never whose**; and because `openspec archive` **always** writes the non-allowlisted `openspec/specs/**`, **any change left open across any other change's archive latches to in-scope permanently.** So an in-scope verdict is **never** evidence that the change's own implementation landed, and **no check may use it as that proxy** (see the range-pollution refutation below).

- **The worker (`/xtty:cross-review <change>`, a main-loop protocol — details in the command).** User-launched only; **one launch authorizes the whole bounded run** (spend human-initiated per run). Three passes: **A** = the Opus critic (conformance); **B** = Codex `adversarial-review --model gpt-5.6-sol` (GPT-family soundness, `xhigh` effort **config-governed** — no per-call effort flag) **backgrounded via the harness's Bash `run_in_background`**, never a subagent (strand refutation); **C** = an **inline** Opus soundness pass (the diversity slice — **not** a new standing agent, per the anti-roster refutation) emitting Codex's real `review-output` schema so B/C are comparable. **Both soundness passes are BRIEFED** — the worker passes a brief (design intent + the specific claims to soundness-check + a digest of any drills the main loop already ran, framed as *claims to challenge*) through the reviewer's focus channel (inline, as the trailing positional on `adversarial-review`), because a bare diff makes the soundness pass review in the dark. The brief is **additive** ("check these claims **and** report anything outside them" — it must not blind the reviewer to an omitted risk), **advisory** (zero gate force, recorded in the ledger header so shared framing is auditable), and does **not** scope the range or change the schema; a finding is **not** flagged as two-model consensus when both passes rest only on the same briefed assertion. It does **not** reach for a write-capable drilling reviewer (`task --write` — rejected: loses the schema, adds a write-safety surface, content-filter-aborts security drills; `research/03-analysis/codex-review-integration-forensics.md`). It reviews a **deterministic best-effort range** (base = parent of the change's `proposal.md`-introducing commit — a positional git rule, **no ownership metadata** — **named in the ledger header** with HEAD + the reviewed file list), merges the passes into **one advisory union ledger** with a **heuristic two-model consensus** flag, iterates a **bounded N = 2** fix→re-review loop then escalates the residual, and **surfaces the complete ledger — every finding, every dismissal + rationale, any escalated residual — on every run**. The header **records the effective model of each soundness pass** (and effort where determinable); a skipped Pass B → the header says **single-model**. **Detectable non-gating degradation:** an unavailable reviewer (no companion resolvable by the version-ordered glob, `codex` absent from PATH, logged out) → skip B, complete on A + C, say so in the header. **Every worker output is advisory** — no verdict/coverage-label/ledger/consensus-flag carries gate force or is read mechanically downstream; **"converged" has no gate force; a dismissal is a proposal, not an accepted state; there is no receipt.**

- **The human-attestation gate task (the change tail).** An in-scope change's `tasks.md` tail keeps its `⟶ xtty-openspec-critic` coherence task **and** carries exactly **one blocking human-attestation cross-review task**, after it and before `⟶ archive-ritual`. It is **HUMAN-ONLY — the model MUST STOP**: it may not tick the task and may not derive/compute/fill the attested value. There is **no auto-firing `⟶ xtty-cross-review` marker** (a paid review that must not fire on task-arrival is neither delegate-to-subagent nor run-inline — the only two things the point-of-tick grammar can express). The human runs `/xtty:cross-review`, reads the complete ledger, runs `scripts/cross-review-digest.sh <change>` themselves, and ticks the task **recording the reviewed-state digest on a delimited attestation line** — a single HTML-comment line `<!-- cross-review-attestation: base=<B> head=<HEAD> digest=<sha256> reviewed=<date> -->` in `tasks.md` (deliberately **not** a separate receipt file).

- **Archive step-0 (the fail-closed precondition — the FIRST act of `⟶ archive-ritual`, BEFORE `openspec archive`).** For an in-scope change, evaluate a precondition whose only inputs are the human's attestation line, the digest from committed deterministic tooling, and git ground truth — it **reads no model-authored artifact**. Run the digest + scope scripts **from the reviewed-base version** wherever a prior committed version exists — **including when the change *modifies* that tooling** (that reviewed-base version is exactly the anchor keeping a checker edit from self-validating); **only a tooling-*introducing* change has no prior version, and the anchor there is human code review of the committed scripts** (a stated bootstrap boundary, not mechanically closed). **Refuse to archive unless all four hold:** (1) the attestation line **exists and is well-formed** (`grep -c '<!-- cross-review-attestation:' openspec/changes/<change>/tasks.md` = 1); (2) the reviewed-state digest **recomputes** (`scripts/cross-review-digest.sh <change>`) and **string-equals** the attested value; (3) the tree/index is **clean** (the digest tool's own dirty-refusal); (4) **exempt-by-act** — the sentinel line is **singular and byte-identical from its introducing commit through archive**: over `git log -p -- openspec/changes/<change>/tasks.md` it is **added exactly once and never deleted/modified** (`adds == 1 && dels == 0`), its introducing commit's `tasks.md` hunk is confined to the **attestation line + checkbox ticks** (no reviewed artifact, no gate implementation), and every later commit touches only the remaining bookkeeping surfaces; any later add/delete/modify of the line **invalidates the attestation** → fresh review + attestation. These four are **accident tripwires + human-legibility aids**, **not** adversarial-integrity guarantees: a repo-controlling model can rewrite history or forge the tick, so adversarial resistance rests on **the human reading the complete ledger** plus the accepted model-only-loop residual (the same trust class the repo already accepts for every committed procedure — a session that ignores `⟶ archive-ritual` is already outside the workflow's contract), never on a mechanical git-provenance check. An **optional strong form** (`git commit -S` over the attestation + `git verify-commit` an allowlisted key, verified when present) is available but **not default** — it only bites at an out-of-band CI/branch-protection or human-run-archive boundary (an in-loop model runs `verify-commit` itself), so it is not worth its ceremony against the repo's $0 ethos.

- **Two axes, honest scope.** The critic checks **conformance** (rulebook + disk-drift) and its **Pass 4** fact-checks a change's *stated claims about existing symbols* (a bounded in-repo check — it does **not** catch a misplaced *new* field, and is blind to external-dependency internals); the cross-model passes check **soundness** (approach/assumptions, source-traced). Complementary, not redundant — the motivating exemplar (a new config key on the wrong owner type) was a **cross-model** catch the critic's code-accuracy pass deliberately cannot make.

## Conventions

- **Commits: [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/)** — `type(scope): description`. Types used so far: `docs` (research/design/openspec content), `feat`/`test` (implementation), `chore` (tooling). Scopes: `research`, `design`, `openspec`, `app`. End commit messages with the `Co-Authored-By` trailer when authored with an AI.
- **Research docs** carry a **Provenance** note (date + how produced) and a **Sources** list; fact-checked claims use ✅/❌/❓. Snapshots are dated and time-sensitive — re-verify versions/latency/pricing before quoting.
- **Engineering bias:** macOS-first; **reuse battle-tested components over hand-rolling** (especially the VT parser — use the Williams state machine via a library); favor **latency and low memory** in every tradeoff.
- **Don't track local tooling — except the version-controlled workflow tooling:** `.claude/` is gitignored **except** two committed sets. (1) This project's own **hand-authored** tooling — `.claude/commands/xtty/` + `.claude/skills/xtty-*/` + `.claude/agents/xtty-*` (the `/xtty:capture-research` command + the `xtty-capture-research` skill + the `xtty-test-validator` agent + its `/xtty:validate` launcher command + the `xtty-ci-investigator` agent + its `/xtty:investigate-ci` launcher command + the `xtty-openspec-critic` agent + its `/xtty:review` launcher command + the `/xtty:research` source-research launcher command — worker is a Workflow, no standing agent — + the `/xtty:cross-review` cross-model-review launcher command, a **main-loop protocol** (not a delegated agent — it drives a detached reviewer + edits artifacts between rounds, which a subagent would strand) whose Pass C soundness reviewer runs **inline**, not as a standing agent, per the anti-roster refutation). Its two committed deterministic gate scripts — `scripts/cross-review-digest.sh` (reviewed-state digest) and `scripts/cross-review-scope.sh` (mechanical scope classifier) — live under `scripts/` (always tracked, outside the `.claude/` exception). (2) The **openspec-generated** workflow tooling — `.claude/commands/opsx/` + `.claude/skills/openspec-*/` — tracked but **pinned to a recorded CLI version** (the `generatedBy` stamp each file carries), so a fresh clone has the `/opsx:*` workflow present and its prompt text can't drift under a silent CLI bump: regenerate it *only* via the explicit `openspec init`/`update` step and **re-commit the diff deliberately** on a version bump (routine `openspec list`/`validate`/`status` are proven to leave the files byte-identical, so day-to-day work produces no spurious diffs). Only machine-local Claude files — `settings.local.json` and runtime locks — stay ignored.
