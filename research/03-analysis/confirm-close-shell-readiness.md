# Confirm-close & shell readiness — the churn flake, the field survey, and the protocol ladder

> **Provenance:** 2026-07-03. `/opsx:explore` "split agent for investigate this flaky" — a 4-agent workflow: (1) a **code signal probe** over the state-dump/close-path sources; (2) a **terminal prior-art survey** reading real source in `/tmp` clones (iTerm2, Ghostty, Kitty, WezTerm); (3) an **empirical pty foreground-pgid probe** replicating xtty's exact launch topology (`pty.fork`, dash-argv0 `-zsh`/`-bash`, the curated `ShellResolver` seed env, `os.tcgetpgrp(master_fd)` polled at 10–25 ms — the identical syscall to `hasForegroundJob`); (4) a **design synthesis**. Triggered by the same-day local churn-test record **F(47 s) / F(37 s) / P(6.8 s)** (three `xcodebuild` runs; the user eyewitnessed the confirm-close alert in both failing runs). Companion to [`github-actions-ci-cd.md`](github-actions-ci-cd.md) §13 (the local race), §15 (the CI menu-clobber mode), §16 (the cross-pointer).

## 1. The problem

`testLifecycleChurnReturnsCensusToBaseline` (the P7c leak-regression net) splits a pane and closes it within ~150–500 ms of registration — but a fresh shell needs seconds to source a heavy `~/.zshrc` (nvm, compinit, zoxide, oh-my-zsh). A startup child owns the PTY foreground at close time, `hasForegroundJob` (`tcgetpgrp(fd) != shellPid`, `App/TerminalWindowController.swift:474`) is true, `confirmClose()`'s `NSAlert` blocks the close, and the census stays one pane high. The **same race exists in the tab-churn loop** (identical `paneRequestsClose → confirmClose` path). It is a race weighted by shell-startup time: warm caches + idle CPU → pass in ~7 s; anything slower → fail in 37–47 s of cascading timeouts. It is also a **real-user papercut**: ⌘W on a just-opened pane mid-`.zshrc` produces a spurious "a process is still running" alert naming `nvm`/`git`.

## 2. Empirical — the foreground-pgid timeline (the probe that killed the obvious fix)

- ✅ **`fg == shellPid` from birth**: the forked shell is the session leader, so `tcgetpgrp` returns the shell's pgid within **3–30 ms of spawn — before `~/.zshrc` runs at all**. A single `hasForegroundJob == false` read is therefore **worthless** as a readiness signal (it's true before startup even begins).
- ✅ **Startup children grab the tty in short bursts**: 15–57 ms episodes (git, nvm, node), with **shell-owned gaps up to ~740 ms between bursts** and the **last flicker as late as ~2.0 s** under 8-core CPU saturation (3 concurrent shells, mimicking churn-under-xcodebuild). Flickers cluster in two bands: rc-sourcing (~200–600 ms) and first-prompt-render/precmd (~1.2–2.0 s) — children grab the foreground **even after the first prompt is visible**.
- ✅ **The 150 ms dump sampler is structurally blind** to 15–57 ms episodes → "k consecutive clean reads" degenerates into a disguised, load-scaled sleep (k=14 ≈ 2.1 s sufficed under synthetic load; a lower bound for cold caches). Do not build assertions that require *observing* these episodes through the dump.
- ✅ **bash (the CI shell): zero flicker** — `fg == shellPid` from <35 ms, uninterrupted for the full 15 s observation. Any pgid-based wait passes instantly under CI bash.
- ✅ **Every observed startup fg episode occurred with ZERO bytes of user input on the PTY** (all 10 runs) — the empirical basis for the zero-input latch idea (§6).
- ❓ The worst-case settle (~2 s) came from synthetic load, not reboot-cold caches; real cold-nvm startups can plausibly exceed it — any wait needs a generous outer timeout (≥10–15 s), not a 2–3 s cliff.

## 3. The dump-freeze finding (why the failing runs were so hard to read)

`App/XttyApp.swift:194` uses `Timer.scheduledTimer(...)`, which registers in the main run loop's **`.default` mode only**. `NSAlert.runModal()` spins `NSModalPanelRunLoopMode`, where default-mode timers **do not fire** — so the instant the alert appears, the state/grid dump files **freeze at their pre-alert content**. Every subsequent `StateDumpReader` poll re-reads frozen JSON; later keystrokes go to the modal; all waits time out; the final census read is the frozen `final 2 vs baseline 1`. This fully explains the stale-dump artifacts that obscured the §13/§15 diagnoses. Fix (companion **F**): construct the timer and `RunLoop.main.add(timer, forMode: .common)` — one DEBUG-only line, valuable independent of which readiness fix ships.

## 4. Prior art — how real terminals decide "safe to close?"

| Terminal | Mechanism | Fresh-shell race? |
|---|---|---|
| **iTerm2** | Per-profile tri-state; **factory default = never prompt**. Opt-in "jobs" mode does a **name-based process-tree walk** (shell excluded, `login`/`iTerm2`/`ShellLauncher` always ignored, user jobs-to-ignore list). `tcgetpgrp`-equivalent used only for tab titles, never the close decision. No creation grace (its 10 s `minRunningTime` guards a different feature). | dodged only by the never-prompt default |
| **Ghostty** | Pure **OSC 133 at-prompt** state (`cursorIsAtPrompt`); no tree walk, no pgid, no names, no grace. **Refuses to inject integration into Apple's `/bin/bash`** (bash 3.2, ENV/--posix path disabled). | would prompt (pre-first-prompt ⇒ "running") |
| **Kitty** | Same protocol gate (`prompt_kind` scan); `tcgetpgrp` only names the process in the dialog text. Plain window close unconfirmed by default. | would prompt |
| **WezTerm** | Whole-tree exe-basename set must be a **subset of `skip_close_confirmation_for_processes_named`** (default: `bash, sh, zsh, fish, tmux, nu, …`). | would prompt (`nvm`/`git`/`brew` aren't on any list) |

✅ **Cross-cutting:** no surveyed terminal uses xtty's bare instantaneous `tcgetpgrp != shellPid` as the decision — the field splits into name-based tree walks and OSC-133 prompt state — **but none fixes the fresh-shell race product-side, and none has a creation-time grace**. xtty prompting on a busy fresh shell is field-consistent, defensible behavior. Fix the test, not (necessarily) the product.

## 5. The fix design — DECIDED (test-side, zero product change)

**Primary — the computed-marker execution roundtrip, in BOTH churn loops:** after the `paneCount==2` (resp. `tabCount==2`) wait, type a **computed** marker into the already-focused fresh pane — `echo $((41000+i))` (pane loop) / `echo $((42000+i))` (tab loop) — and `GridDumpReader.waitForContains("410 0i", timeout: 15, ignoringLineWraps: true)` **before** ⌘W; on timeout, fail fast with an attached grid dump and never send ⌘W (so a readiness failure can't cascade into the modal-wedge artifact). Why it's right:

- The output token (`41001`) **never appears in the echoed input line** (`echo $((41000+1))`) — a match proves the shell **read and executed** a command, i.e. rc files are complete and the shell is back at its prompt (`echo` is a builtin; it never changes the fg pgrp). An execution **event**, strictly later than the last rc-sourcing flicker — not a flappy state.
- **Shell-agnostic**: `$(( ))` arithmetic is identical in bash and zsh; under CI bash the roundtrip is instant (<35 ms settle, zero flicker). No OSC 133 dependency.
- **Intent-preserving**: `confirm-close` stays at its user default; the close stays the real ⌘W keybinding path; the census assertion is untouched.
- **In-repo prior art**: the multiplexing split test never flakes locally *because* it types `SPLITMARK` before closing (`XttyMultiplexingUITests.swift:29-31`); quake does the same with `QUAKEMARK`. (The computed marker is the echo-proof upgrade of that pattern.)
- **Numbers**: 15 s timeout ≈ 7.5× the worst measured settle; unique per-iteration markers make stale-dump false-positives impossible; warm cost ≈ +0.5–1 s/iteration.

**Companion F** — the dump-timer `.common`-modes fix (§3). **Pre-planned escalation (not shipped speculatively)** — if a residual flake is ever observed (the post-marker precmd window): add a one-line `hasForegroundJob` field to the state dump (public SwiftTerm API: `process.shellPid`/`childfd`) + a single post-marker `hasForegroundJob == false` wait — a single read **is** meaningful post-marker, unlike pre-marker.

**Rejected, with evidence:** ❌ waits on `sessionActivity`/`runningCommand`/blocks or a sentinel-command *block* completion — all OSC-133-derived, structurally blind to startup (activity reads `idle` mid-`.zshrc`) **and inert under CI bash**; ❌ `confirm-close = false` opt-out — removes the very branch the leak net exercises, and the prior art confirms the prompt is legitimate behavior (also: it would have masked the alert-wedge bug class the frozen dump just demonstrated); ❌ prior-art product mechanisms as the flake fix — skip lists/name walks don't cover `nvm`/`git`/`brew`, and no terminal ships a creation grace. **Note:** this fix alone does **not** green the churn test on CI — there it dies earlier via the §15 menu clobber; the combined green needs both.

## 6. The protocol ladder — the "real protocol" beyond the flake fix

The real protocol for shell readiness is **OSC 133 semantic prompts** (FinalTerm; iTerm2/VS Code/WezTerm/Kitty/Ghostty). xtty already implements the capture side (P4a) — `BlockTracker` carries the exact tri-state the field gates on: `private enum Phase { idle, atPrompt, running }` (`XttyCore/Sources/XttyCore/Block.swift:99`), where `idle` = *no prompt seen yet* (fresh shell) and `atPrompt` = first `133;A` seen. The ladder, cheapest → most complete:

| Layer | What | Status |
|---|---|---|
| 1 | Marker roundtrip in the churn test (§5) | **decided** — the bridge wherever the protocol is absent (CI bash today) |
| 2 | **Confirm-close gates on `atPrompt`** — prompt iff `hasForegroundJob` AND `phase != .atPrompt` when integration is active (the Ghostty/Kitty model) | candidate product change — protocol-following, small (the state machine exists; it's `private` and unconsulted). Kills *post*-prompt false positives (e.g. prompt-render `git` children). **Does not fix mid-startup**: the protocol is silent until the first `133;A` — by design, everywhere in the field |
| 3 | **Bash shell integration** — `bash-preexec` via the `--init-file` route (VS Code/iTerm2 pattern; ENV injection is impossible on Apple's bash 3.2, per Ghostty's explicit refusal) | candidate capability (`shell-integration` delta) — **protocol-complete**: `133;A` fires under bash too, so the churn test can wait on the *protocol* signal everywhere and the §5 marker becomes retirable; also lights up blocks/sidebar/cwd for bash users — on-mission (agent CLIs commonly run bash) |
| — | **E2: the zero-input latch** — confirm only if `hasForegroundJob && userHasInteracted` (latch set at `keyDown`/paste — never the terminal→host byte stream, which auto-replies to DA/DSR/OSC with zero user involvement; seeded **true** for profile-`command` panes) | candidate product change — **empirically grounded** (§2: every startup fg episode had zero PTY input; a foreground child on a never-typed pane cannot be a user job) and **the only option that fixes the mid-startup ⌘W papercut**. ❓ Novel — no field precedent; needs its own change + adversarial review (IME/marked-text, quake panes, `XTTY_TEST_*` triggers, rc files that intentionally launch foreground work) |

**Sequencing decision:** the §5 marker fix (test-only) ships with the §15 menu-clobber work now; layers 2/3 and E2 are **captured candidates**, each its own future OpenSpec change, none gating the flake fix.

## 7. Addendum (2026-07-03) — artifact verification: the design confirmed against the three local runs

> **Provenance:** same day, after §1–§6 settled. Read the three local `.xcresult` bundles (16:41 **F** 45.8 s / 16:44 **F** 35.7 s / 16:47 **P** 5.4 s) at per-keystroke resolution via `xcresulttool get test-results activities` + exported attachments.

- ✅ **The per-iteration coin flip is artifact-confirmed.** Run 1: pane iterations 1–3 closed clean (waits passed instantly = live dump transitions), the alert struck at **pane iteration 4's ⌘W** (fired 0.17 s post-split). Run 2: the **entire pane loop clean**, alert struck at **tab iteration 2's ⌘W** — the tab-loop race observed in the wild, validating §5's both-loops gate. Run 3: all 7 cycles clean, 14 keystrokes in 4.9 s. Strike rate ≈ 1 in 7–11 closes, consistent with §2's 4–12 % child-owned-fg fraction; every ⌘W fired 0.2–0.6 s post-split — inside the 200–600 ms rc-sourcing flicker band.
- ✅ **The frozen-dump model (§3) is confirmed behaviorally:** post-alert waits alternate instant-pass (waiting for the value the file froze at) and exactly-5 s timeout (waiting for a value that can never appear) — run 1's 45.8 s decodes as 5 s + tab-loop alternation + the 20.3 s settle poll; run 2's 35.7 s as 5.3 s + 5 s + 20.3 s. *(Timing-signature evidence; the frozen JSON itself is transient and unrecoverable post-hoc.)*
- ✅ **The stuck-type census composition decodes exactly:** run 1 stuck 3 types (one pane's worth; no `TerminalWindowController` because the post-alert ⌘T's went into the modal — no tab ever opened); run 2 stuck 4 (the blocked tab's window controller + its pane's worth).
- ✅ **Fail-fast justified:** 4–6 post-alert keystrokes went uselessly into the modal in each failing run — the §5 fail-fast eliminates that noise and localizes the failure to its iteration.
- ✅ **§13b display-blindness re-confirmed:** the `after-churn` screenshot captured the **main/external** display (the dev editor session), not xtty and not the alert — local visual artifacts remain useless for this bug; timelines + failure messages are the evidence channel.
- **Net:** in both failing runs the §5 marker gate would have held ⌘W past the exact iteration that was struck — the decided fix addresses the *observed* failure mode, not a theorized one.
