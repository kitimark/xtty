# OpenSpec coherence checklist — what to update when a requirement changes

**Relocated 2026-07-17** from `AGENTS.md`'s OpenSpec workflow section (a `/doctor` check-4 lazy-loading
migration — this is pure procedure, consulted only when authoring or reviewing a spec delta, not
decision-time content that needs to be eager every session). Nothing here is new; it is the walk-list
verbatim, moved so it costs context only when `xtty-openspec-critic` or a human actually runs it. The two
cheapest, highest-consequence gotchas (scenarios need exactly 4 hashtags; a MODIFIED requirement must paste
the entire existing block) stay stated inline in `AGENTS.md` next to the spec delta format — this doc holds
the rest.

## The checklist

The four artifacts are a dependency chain (`proposal → design + specs → tasks`), so a requirement edit
rarely lives alone. When you add/modify/remove a requirement in `changes/<name>/specs/`, walk this list,
then run `openspec validate "<name>"` (it catches missing deltas/scenarios):

- **`proposal.md` → Capabilities** is the contract with `specs/`: every capability a spec delta touches MUST appear under **New** or **Modified Capabilities** (and vice-versa — no orphan spec dir, no listed-but-absent capability). Refresh **What Changes** / **Impact** if scope moved.
- **`specs/<capability>/spec.md`** — keep requirements **mechanism-neutral (the *what*)**; the *how* (fork vs seam, file/type names, concrete APIs) belongs in `design.md`, never inside a requirement. A **MODIFIED** requirement MUST paste the **entire** existing block from `openspec/specs/<capability>/spec.md` and edit it (partial content silently loses detail at archive). A behavioral change usually spans **multiple capabilities** — e.g. a new keybind action also touches `terminal-keybindings`; a new config key touches `terminal-configuration`.
- **`verification-harness` (almost always, in this repo)** — the custom-drawn view exposes nothing to accessibility, so any **new observable behavior** needs *both* a `verification-harness` spec delta (a new DEBUG state-dump field/observation + an e2e scenario) **and** a harness task. 26 of the 58 archived changes carried a harness delta for exactly this reason — if the harness can't see it, it isn't done.
- **Test precision vs. the claim (design-time, Decisions).** When a change adds or modifies a test, `design.md`'s Decisions (or Risks/Trade-offs) MUST state (1) the exact claim the test proves, (2) the layer/mechanism that claim lives in, and (3) why the chosen driver reaches that layer. Then match the test's depth to the claim — symmetrically: an over-deep test is as wrong as a too-shallow one, and this is not a "prefer synthetic/low-level tests" rule. Decide by where the claim lives. A real end-to-end program is the right tool for a claim that lives upstream of any program-specific behavior — e.g. `testWheelScrollsRealMouseTrackingPager` drives real `less --mouse` to prove wheel routing (whether a mouse report reaches the program at all, decided before any redraw), so the program's own escape idiom is irrelevant and the real program is exactly right. A direct/synthetic driver is the right tool for a claim about one narrow internal code path a given program may or may not exercise — e.g. in `fix-scroll-reversal-redraw-corruption` only htop's ncurses hardware-scroll optimizer hits the buggy `cmdScrollDown` (`vim` uses already-guarded `IL`/`DL`, `less` a bare `RI` with no scroll region), so a real-pager test would pass green while proving nothing; the fix is instead proven by driving the exact `SU`/`SD`-inside-a-scroll-region sequence directly via `printf`. The trap runs both directions: a driver — real program or synthetic — can silently fail to exercise the intended mechanism because the escape-idiom choice (a real program's, or your own hand-written sequence's) may not match the path under test, and a program's idiom is outside this project's control. Worked exemplars already living in Decisions/Risks (no new machinery): `split-shell-dependent-testplan` D2 (assert forwarding fidelity per the shell's observed capability), `fix-scroll-wheel-mouse-reporting` Risks (assert the deterministic routing state-dump field, not a program's own scroll count).
- **`design.md`** — re-check that decisions and requirements still justify each other *both ways*: a changed decision can leave a requirement over-/under-specified (neutralize it — e.g. drop a hard-coded mechanism), and a new requirement may need a decision plus a Risks / Migration / Open-Questions update.
- **`tasks.md`** — every requirement needs build **and** verify tasks; add or re-order them when requirements change (and split deferred work into its own task group rather than blurring scope). Any verify task that runs the **Tier-1 XCUITest suite (`make test`), a VM tier, or a full acceptance matrix** MUST carry the delegation marker `⟶ xtty-test-validator (<tier/scope>)` (see the test-validation rule in **`AGENTS.md`'s "How to work here"** section for the inline-vs-delegate boundary); cheap checks stay unmarked. A change's **completion** MUST carry an explicit **archive + reconcile** task marked `⟶ archive-ritual` (the *standard change tail* — placed after its pre-archive `⟶ xtty-openspec-critic (<change>)` coherence task), so `/opsx:propose` emits it and `xtty-openspec-critic` flags its absence; that marker points to the **committed hand-authored** archive ritual (see **`AGENTS.md`'s "Keep progress current"** rule), not the CLI-generated archive skill (tracked now, but regenerable by `openspec init`/`update`).
- **`research/`** — the *why* stays in `research/` (update the relevant doc **and** its `research/README.md` line when a decision/finding shifts); the actionable *decision* stays in the change. Trackers (**`AGENTS.md`'s** Current status, the milestone state) are updated on completion per **`AGENTS.md`'s "Keep progress current"** rule.
