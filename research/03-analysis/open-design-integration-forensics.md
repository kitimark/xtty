## Mechanism / internals (✅ verified from source + live execution)

### Two integration modes exist; only one is ready without extra setup
(A) **Desktop Studio app** — PATH-scans for coding-agent CLIs at onboarding and spawns the user's own authenticated `claude` binary for generation. Zero extra setup; this is the mode the whole rest of this document concerns. (B) **MCP-into-Claude-Code**, via the `od` CLI — not brew-installable (no Homebrew formula; the name collides with coreutils `/usr/bin/od`), so it needs a real setup project (Docker or build-from-source). Turned out easier than first assumed: `Settings → MCP server` in the installed app gives an absolute-path client snippet and Claude Code specifically gets a `claude mcp add-json` one-liner (`README.md:302-306,323-326,398`), sidestepping the PATH collision entirely — but this was never exercised in the POC; mode (A) covered everything needed.

### Output is HTML by design, even for "native" briefs — mechanically agnostic, productively web-only
The Claude runtime adapter (`apps/daemon/src/runtimes/defs/claude.ts:52-89`) is a thin wrapper spawning the literal `claude` CLI in print-mode (`-p --input-format stream-json --output-format stream-json --verbose`), with `--permission-mode bypassPermissions` appended unconditionally (`claude.ts:87`). Nothing about that spawn is web-specific — such a process could edit any file in its working directory, including `.swift` files. But the *composed prompt* is unconditionally HTML-bound: the core charter states the deliverable outright — *"You are an expert designer working with the user as your manager, delivering in HTML. HTML is your tool, not your medium"* (`apps/daemon/src/prompts/core-slim.ts`, `SLIM_CORE_CHARTER`, ~line 71) — and even explicitly native briefs are shipped as HTML simulations (`PLATFORM_CONTRACTS_BLOCK`, ~line 180: an iOS brief produces `mobile-ios.html` with "iPhone frame + Dynamic Island + 44px targets"). The entire preview/export/HyperFrames pipeline renders HTML; a `.swift` file written by the spawned agent would be invisible to it. **Conclusion:** Open Design is mechanically stack-agnostic but productively web-only — its coherent use for a native app is HTML mockups that get hand-translated afterward, never direct source edits.

### DESIGN.md/token-package creation has exactly three paths, and none apply to a native macOS app
1. **Hand/agent-authored curation** — how the entire 151-package bundled catalog (including "apple" and "warp") was made; every manifest records `source.type: "bundled"` / `"Open Design curated bundled fixture"` (`design-systems/apple/manifest.json`, `design-systems/warp/manifest.json`) — prose, not a tool extraction.
2. **`brand-extract` skill** — strictly URL-based: drives a live website open in an in-app browser, measuring DOM/CSS (`skills/brand-extract/SKILL.md:31-38,60-70`). No screenshot/image-input variant exists. Inapplicable — xtty has no website.
3. **`od design-systems import-local`/`import-github`** — a deterministic scan of `.css/.scss/.sass/.less` + `.tsx/.jsx/.vue/.svelte` only (`apps/daemon/src/design-systems/import.ts:110-117`). Run against xtty's Swift tree it would find zero tokens and zero components.

**Conclusion:** the design base must be hand-authored by reading the real source; this is exactly what the POC did (`design/xtty/DESIGN.md`, 9 H2 sections, `manifest.json`, `tokens.css`, cited `path:line` throughout against `App/*.swift`/`XttyConfig.swift`/`XttyProfile.swift` @ `b0e3998`).

### There is no OS-level sandbox, and folder scoping bounds blast radius, not the theoretical risk
`--permission-mode bypassPermissions` (`claude.ts:87`) strips Claude Code's own confirmation prompts entirely. `OD_SANDBOX_MODE` (`apps/daemon/src/sandbox-mode.ts`, read in full) sounds like a jail but isn't one: `isSandboxModeEnabled()` gates only (a) redirecting `HOME`/`XDG_CONFIG_HOME`/`XDG_CACHE_HOME`/`TMPDIR`/`CLAUDE_CONFIG_DIR` to an isolated area (so a run can't read/write the user's *real* global Claude Code config or credentials), and (b) which folders are even *allowed* to be selected as an import/project-location root (`isSandboxImportedProjectRootAllowed`). Neither restricts what the spawned process can actually read/write on disk once running — that's ordinary OS file permissions, same as running `claude --permission-mode bypassPermissions` yourself in a terminal. Folder-imported/project-location projects resolve `metadata.baseDir` directly, no copy or shadow tree (`apps/daemon/src/projects.ts`, `resolveProjectDir` → `path.normalize(baseDir)`); the only always-on guard blocks hidden (dotfile) path segments (`projects.ts:80-94`), which does not protect tracked source.

### `.od-skills/` is a disposable per-turn write-barrier, not project content
`apps/daemon/src/cwd-aliases.ts` (read in full): the active skill is staged into the project cwd once per turn — "the previous-turn copy is replaced wholesale on every call." It exists specifically because an earlier symlink-based draft (PR #435 round 1) was flagged as a write-amplification vulnerability: an agent with cwd write access could mutate the *shipped* skill resource through the symlink; per-project copies contain that blast radius ("corrupting it has no effect on other projects or on the source"). Folder names are content-hashed (`skillCwdAliasSegment` — a sha256 digest of the absolute source path), fully reproducible from the app's own installation. **Conclusion:** nothing here is xtty-specific or worth version-controlling — equivalent to a build cache. `design/mockups/.gitignore` excluded `.od-skills/` for exactly this reason.

## Retired theories (fates table)

| Theory | Status | Killed by |
|---|---|---|
| Open Design can derive an xtty DESIGN.md automatically (`brand-extract` or `import-local` against the Swift source) | ❌ Refuted | Source read of `skills/brand-extract/SKILL.md` (URL-only) and `apps/daemon/src/design-systems/import.ts` (CSS/JS-family extensions only) |
| Open Design's spawned agent could safely restyle xtty's Swift files directly, since the runtime is just the general-purpose `claude` CLI | ❌ Rejected on design grounds | `core-slim.ts`'s charter ties the entire preview/export pipeline to HTML; a Swift edit would be invisible to it |
| Selecting "xtty" as the project's design system (the formal picker) is what caused the mockup to use xtty's real colors | ❌ Refuted | `app.sqlite`'s `projects.design_system_id` for the actual project is `null`; palette accuracy came from the agent independently reading `design/xtty/tokens.css`, evidenced in its own message trace |
| `OD_SANDBOX_MODE` provides OS-level sandboxing of the spawned agent's file access | ❌ Refuted | Full read of `sandbox-mode.ts`: only redirects HOME/config paths and gates *which folders can be chosen*; no runtime file-access enforcement |
| Scoping a project to a small subfolder (e.g. `design/mockups/`) fully contains what the spawned agent can touch | ❌ Refuted, then empirically confirmed live | The POC's own agent read a sibling folder (`design/xtty/`) outside its assigned project directory, unprompted — the folder boundary is not enforced, though this specific read was benign |
| `.od-skills/` folders dropped into a project directory are meaningful, version-control-worthy project content | ❌ Refuted | `cwd-aliases.ts` — per-turn disposable copy, "replaced wholesale on every call," content-hashed and fully reproducible from the app's own install |

## Re-verify by effect
- **"No OS sandbox"** → point Open Design at a small scratch folder and ask it to read a file one directory up (a sibling); if it succeeds, the boundary still isn't enforced.
- **"`design_system_id` doesn't drive a folder-linked project's token accuracy"** → `sqlite3 app.sqlite "SELECT design_system_id FROM projects WHERE id='<id>';"` against any folder-linked project, compared against whether its output nonetheless matches a design system's tokens.
- **"`.od-skills/` is disposable"** → delete it, run another turn in the same project, confirm it reappears (folder name changes only if the source skill's absolute path changes).

## Reusable guidelines
1. For a native (non-web) app, hand-author the DESIGN.md/tokens.css design base by reading the real source — no Open Design tool can derive one automatically for it.
2. Treat every Open Design project as running an unsandboxed, confirmation-free coding agent: scope it to a small, dedicated, otherwise-empty folder (never the repo root), understand that this bounds blast radius rather than eliminating the theoretical risk, and `.gitignore` `.od-skills/` inside any such folder.
3. Don't assume the formal design-system picker is what applied a palette to a folder-linked project's output — verify from the project's own DB record and the agent's message trace if precision matters; the agent may find and use project-adjacent files on its own.
4. Open Design's coherent role for xtty is HTML mockup exploration that gets hand-translated into SwiftUI afterward — never a path to direct Swift edits.
