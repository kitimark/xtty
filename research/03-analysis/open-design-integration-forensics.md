## Mechanism / internals (✅ verified from source + live execution)

### Two integration modes exist — and they are not alternatives  ⟲ 2026-07-29
(A) **Desktop Studio app** — PATH-scans for coding-agent CLIs at onboarding and spawns the user's own authenticated `claude` binary for generation. Zero extra setup; this is the mode the whole rest of this document concerns.

(B) **MCP-into-Claude-Code**, via `od mcp`. The `od` *name* does collide with the system octal-dump utility (`which -a od` → only `/usr/bin/od`), but the original claim that mode B therefore "needs a real setup project (Docker or build-from-source)" is **❌ refuted**: the MCP server binary already ships inside the installed app, and the running daemon hands out a ready absolute-path launch spec — `curl -s -H 'Origin: http://127.0.0.1:<port>' http://127.0.0.1:<port>/api/mcp/install-info` returns `command` = the packaged Helper binary, `args` = `[.../prebundled/daemon/daemon-cli.mjs, mcp]`, `cliExists:true`, `buildHint:null`. Nothing is built, fetched, or containerized.

Three properties the original framing missed:
- **B strictly requires A.** `od mcp` is a *stateless proxy* — every one of its 18 tools is a `fetch()` against the daemon (`apps/daemon/src/mcp.ts:1-11`, `:1478-1485`), and on this machine the daemon **is** the desktop app's packaged sidecar (`ps aux` → `daemon-sidecar.mjs --od-stamp-source=packaged`). Quit the app and every tool fails. B is a remote control for A, never a substitute.
- **It is not read-only**, despite the README's framing: 7 of the 18 tools are write-annotated, including `write_file`, `delete_file`, `delete_project` (`mcp.ts:305-483`) and `start_run` — which commissions the daemon to spawn its own `bypassPermissions` agent (`mcp.ts:396-403`). The proxied project API carries no bearer token on loopback.
- **The installer hardcodes `--scope user`** (`mcp-agent-install.ts:158`) — 18 tool schemas plus a ~90-line instruction block injected into *every* Claude Code session in *every* repo.

**Decision (2026-07-29): do not install.** For a folder-linked project whose mockups land in the repo working tree, the MCP adds nothing a plain `Read`/`Grep` doesn't already give, while costing per-session context in unrelated repos and widening the write surface. Revisit only if the loop switches to *managed* projects (artifacts inside the app data dir, where `get_artifact` becomes the only access path) or if GUI round-trips get frequent enough that driving runs from a session pays for itself. Verify any future install by effect: quit the app and confirm the tools fail.

### Output is HTML by design, even for "native" briefs — mechanically agnostic, productively web-only
The Claude runtime adapter (`apps/daemon/src/runtimes/defs/claude.ts:52-89`) is a thin wrapper spawning the literal `claude` CLI in print-mode (`-p --input-format stream-json --output-format stream-json --verbose`), with `--permission-mode bypassPermissions` appended unconditionally (`claude.ts:87`). Nothing about that spawn is web-specific — such a process could edit any file in its working directory, including `.swift` files. But the *composed prompt* is unconditionally HTML-bound: the core charter states the deliverable outright — *"You are an expert designer working with the user as your manager, delivering in HTML. HTML is your tool, not your medium"* (`apps/daemon/src/prompts/core-slim.ts`, `SLIM_CORE_CHARTER`, ~line 71) — and even explicitly native briefs are shipped as HTML simulations (`PLATFORM_CONTRACTS_BLOCK`, ~line 180: an iOS brief produces `mobile-ios.html` with "iPhone frame + Dynamic Island + 44px targets"). The entire preview/export/HyperFrames pipeline renders HTML; a `.swift` file written by the spawned agent would be invisible to it. **Conclusion:** Open Design is mechanically stack-agnostic but productively web-only — its coherent use for a native app is HTML mockups that get hand-translated afterward, never direct source edits.

### DESIGN.md/token-package *derivation* has exactly three paths, and none apply to a native macOS app
*(Heading narrowed ⟲ 2026-07-29: this section is about **deriving** a package from an existing artifact. Getting an already-authored package **into** the app is a separate, well-supported problem — see "Registration" below. The original wording invited the wrong inference that a hand-authored package can't be installed.)*

1. **Hand/agent-authored curation** — how the entire 151-package bundled catalog (including "apple" and "warp") was made; every manifest records `source.type: "bundled"` / `"Open Design curated bundled fixture"` (`design-systems/apple/manifest.json`, `design-systems/warp/manifest.json`) — prose, not a tool extraction.
2. **`brand-extract` skill** — strictly URL-based: drives a live website open in an in-app browser, measuring DOM/CSS (`skills/brand-extract/SKILL.md:31-38,60-70`). No screenshot/image-input variant exists. Inapplicable — xtty has no website.
3. **`od design-systems import-local`/`import-github`** — a deterministic scan of `.css/.scss/.sass/.less` + `.tsx/.jsx/.vue/.svelte` only (`apps/daemon/src/design-systems/import.ts:114` `STYLE_EXTENSIONS`, `:115` `COMPONENT_EXTENSIONS` — the original `:110-117` citation brackets the truth but points partly at the `IGNORED_DIRS` set above it). Run against xtty's Swift tree it would find zero tokens and zero components.

> **Pre-emptive note (so the refutation isn't mistakenly reopened):** the daemon *does* ship a SwiftUI `Color(...)` parser — `apps/daemon/src/design-systems/swift-colors.ts`, handling `red:green:blue:`, `hue:saturation:brightness:`, and `white:`. It is **not** an importer. Its only caller is `extractSwatches`, which reads the **markdown body of DESIGN.md** to build the picker's 4-colour thumbnail row (`design-systems/index.ts:3822`, docstring at `:3762-3774`) — never a Swift source tree. Useful upshot: if DESIGN.md *quotes* xtty's `Color(...)` declarations verbatim, the picker derives swatches from them for free.

**Conclusion:** the design base must be hand-authored by reading the real source; this is exactly what the POC did (`design/xtty/DESIGN.md`, 9 H2 sections, `manifest.json`, `tokens.css`, cited `path:line` throughout against `App/*.swift`/`XttyConfig.swift`/`XttyProfile.swift` @ `b0e3998`).

### Registration: four supported routes ingest an already-authored package  ⟲ 2026-07-29 (new)
Derivation ≠ registration. Any of these installs a hand-authored package without deriving anything:
1. **Local install by symlink** — `library-install.ts:133-181`, `fs.symlinkSync(realPath, linkPath, 'junction')` at `:175`, naming the folder `path.basename(source)`. Discovery explicitly honours symlinks (`design-systems/index.ts:277`). **This is the route to use**: repo and app become the same bytes, so drift is impossible at this layer.
2. **GitHub install by clone** — `library-install.ts:74-96`.
3. **`POST /api/design-systems`** → `createUserDesignSystem` (`design-systems/index.ts:1154-1197`) writes `DESIGN.md` verbatim from a supplied body and registers `user:<slug>`; surfaced in the UI via Settings → Design Systems.
4. **Plain manual placement** into `data/design-systems/<slug>/` — discovery is a bare `readdir` (`index.ts:269-285`).

⚠️ **Never** use "Import from folder"/`import-local` on a hand-authored package — that is route 3 of *derivation*, and it regenerates DESIGN.md from a CSS/JS scan, destroying the authored prose.

### `tokens.css` answers to a machine-enforced token schema  ⟲ 2026-07-29 (new — a gap in the original capture)
`packages/contracts/src/design-systems/token-schema.ts` declares **56 tokens across 4 layers** (measured: 8 `A1-identity`, 18 `A1-structure`, 26 `A2`, 4 `B-slot`), with A2 documented as "required-with-fallback rather than optional" (`:39-48`). A package that only defines the tokens it happens to care about leaves pasted artifacts with `var()` targets that silently resolve to nothing.

Two concrete traps the POC's own `tokens.css` fell into, both invisible at authoring time:
- **`--font-chrome` is not a token.** The schema defines exactly three font slots — `--font-display` (`:136`), `--font-body` (`:137`), `--font-mono` (`:138`). The POC's package bound `--font-chrome` and the generated mockup dutifully referenced `var(--font-chrome)`; it was off-schema on both sides.
- **`#242628` has no source in xtty.** `grep -rn '242628' App/ XttyCore/` returns nothing — xtty defines no chrome surface colour at all (its only literal colours are `XttyConfig.swift:38-72` and `SpatialToast.swift:24`). It was a *derived* value presented in the probes table alongside genuinely cited ones. A re-authored package must annotate derived values as derived.

### The design-system picker is the whole tokens-into-prompt channel  ⟲ 2026-07-29 (new — answers an open question below)
The original capture left "whether explicitly setting the formal design-system picker changes anything" as an open question, having observed correct colours with `design_system_id = null`. It changes *everything*: selecting a system is what causes the daemon to paste **the entire DESIGN.md and the entire tokens.css verbatim into the system prompt**, with explicit anti-invention imperatives (`apps/daemon/src/prompts/system.ts:1129-1131`, `:1151-1155`), plus the USAGE.md, import-mode, component-manifest/fixture and pull-index blocks (`:1121-1127`, `:1133-1138`, `:1157-1168`, `:1170-1174`). The channel is gated on a non-null `effectiveDesignSystemId` **and** a non-draft status (`server.ts:3889-3915`; `server-services.ts:171`).

So the POC's fidelity was **luck, not mechanism** — a null `design_system_id` means tokens.css never entered the prompt at all, and the palette match came entirely from the agent's opportunistic sibling-file read. Two independent reasons the picker *mechanically could not* have been responsible:
- `null` explicitly means "No design system", with the app default deliberately **not** reapplied (`server.ts:3619-3629`).
- A package carrying no `metadata.json` is status `draft`, and drafts are rejected at selection with `DESIGN_SYSTEM_NOT_PUBLISHED` (`server-services.ts:122-127`, `:171-173`, `:193-199`). The POC's three-file package **was not even selectable.**

Practical consequences for the real setup: `metadata.json` must carry `"status":"published"` (else the picker rejects it) and `"artifactMode":"agent-managed"` (else the app generates ~23 scaffolding files into the folder). Note also that `metadata.json` is **app-owned on write-back** — on the first run the daemon rewrites the whole file through the symlink as `JSON.stringify(…, null, 2)` of a 9-key allowlist (`title, category, surface, status, artifactMode, createdAt, updatedAt, provenance, projectId`); any other key is silently deleted, so author those keys only, 2-space indent, and expect an added `projectId` line as the first-run diff.

### There is no OS-level sandbox, and folder scoping bounds blast radius, not the theoretical risk
`--permission-mode bypassPermissions` (`claude.ts:87`) strips Claude Code's own confirmation prompts entirely. `OD_SANDBOX_MODE` (`apps/daemon/src/sandbox-mode.ts`, read in full) sounds like a jail but isn't one: `isSandboxModeEnabled()` gates only (a) redirecting `HOME`/`XDG_CONFIG_HOME`/`XDG_CACHE_HOME`/`TMPDIR`/`CLAUDE_CONFIG_DIR` to an isolated area (so a run can't read/write the user's *real* global Claude Code config or credentials), and (b) which folders are even *allowed* to be selected as an import/project-location root (`isSandboxImportedProjectRootAllowed`). Neither restricts what the spawned process can actually read/write on disk once running — that's ordinary OS file permissions, same as running `claude --permission-mode bypassPermissions` yourself in a terminal. Folder-imported/project-location projects resolve `metadata.baseDir` directly, no copy or shadow tree (`apps/daemon/src/projects.ts`, `resolveProjectDir` → `path.normalize(baseDir)`); the only always-on guard blocks hidden (dotfile) path segments (`projects.ts:80-94`).

⟲ **2026-07-29 — that last guard is weaker than "does not protect tracked source" suggests: it protects nothing at all from the spawned agent.** `grep -rn "assertVisibleForImportedProject" apps/daemon/src` returns 9 hits, *all* inside `projects.ts` and **zero** in the runtime/spawn path. It guards the daemon's own file API (and therefore also what the telemetry object-uploader can read) — the agent's own Read/Write/Bash tools never pass through it. Don't read it as a dotfile shield.

⟲ **2026-07-29 — `OD_SANDBOX_MODE` is worse than "not a jail": it is auth-severing.** Measured under its exact env (`sandbox-mode.ts:175-192`), `claude auth status` goes `{loggedIn:true, subscriptionType:'max'}` → `{loggedIn:false, authMethod:'none'}`, with the `HOME` redirect (`:178`) and the `CLAUDE_CONFIG_DIR` redirect (`:188`) each sufficient alone. Generation would simply not run. A negative grep across the packaged/desktop/web surfaces also found no desktop wiring that reaches it. It is retired, not an option — see the fates table.

### `.od-skills/` is a disposable per-turn write-barrier, not project content
`apps/daemon/src/cwd-aliases.ts` (read in full): the active skill is staged into the project cwd once per turn — "the previous-turn copy is replaced wholesale on every call." It exists specifically because an earlier symlink-based draft (PR #435 round 1) was flagged as a write-amplification vulnerability: an agent with cwd write access could mutate the *shipped* skill resource through the symlink; per-project copies contain that blast radius ("corrupting it has no effect on other projects or on the source"). Folder names are content-hashed (`skillCwdAliasSegment` — a sha256 digest of the absolute source path), fully reproducible from the app's own installation. **Conclusion:** nothing here is xtty-specific or worth version-controlling — equivalent to a build cache.

⟲ **2026-07-29 — two corrections.** (1) The original sentence "`design/mockups/.gitignore` excluded `.od-skills/` for exactly this reason" is **unsupported and probably wrong**: an in-run `ls -la design/mockups/` captured in the run trace lists exactly two entries — `.od-skills` and `README.md`, no `.gitignore` — and `git log --all -- design/` is empty, so no such file ever reached git. Treat the ignore rule as *unwritten work that must be created before the folder is recreated*, not as an existing artifact. (2) `.od-skills/` is **not** the only untracked write the charter produces: it also emits `brand-spec.md` (`core-slim.ts:127`), `-v2` duplicate files (`:163`), curl'd remote images (`:158`), and a `<name>.html.artifact.json` sidecar per artifact (`projects.ts:862-866`, always reached via `artifacts/create.ts:74`). Scope the ignore rule to the whole project folder's *machine-local* residue, not one subdirectory.

## Re-verify by effect
- **"No OS sandbox"** → point Open Design at a small scratch folder and ask it to read a file one directory up (a sibling); if it succeeds, the boundary still isn't enforced.
- **"`design_system_id` doesn't drive a folder-linked project's token accuracy"** → `sqlite3 app.sqlite "SELECT design_system_id FROM projects WHERE id='<id>';"` against any folder-linked project, compared against whether its output nonetheless matches a design system's tokens.
- **"`.od-skills/` is disposable"** → delete it, run another turn in the same project, confirm it reappears (folder name changes only if the source skill's absolute path changes).
- ⟲ **"The picker is the tokens channel"** → the DB read is only a *precondition* (it still reads `user:xtty` if the symlink dangles or the package regresses to draft, while the daemon composes zero design-system blocks). The real gate is the artifact: generated HTML must contain the pasted `:root` block **and a token value unique to our tokens.css**. Change one token value in the repo, regenerate, and grep the output for the new value.
- ⟲ **"Content telemetry is off"** → never trust the API echo; re-read `app-config.json` on disk and assert `telemetry.content === false`. Note this is a *prevention-only* control — there is no local send-log, so it cannot be verified retroactively for past runs.
- ⟲ **"MCP is not installed / is not needed"** → if ever installed, quit Open Design.app and confirm every `od mcp` tool fails; that failure *is* the proof it was only ever a remote control for the GUI.

## Reusable guidelines
1. For a native (non-web) app, hand-author the DESIGN.md/tokens.css design base by reading the real source — no Open Design tool can derive one automatically for it.
2. Treat every Open Design project as running an unsandboxed, confirmation-free coding agent: scope it to a small, dedicated, otherwise-empty folder (never the repo root), understand that this bounds blast radius rather than eliminating the theoretical risk, and write the ignore rules **before** the folder is created. ⟲ *Amplified 2026-07-29:* `.od-skills/` alone is not enough (the charter also writes `brand-spec.md`, `-v2` duplicates, fetched images and `*.artifact.json` sidecars), and since folder scope is not enforced, pair it with a **detect-and-revert** posture — clean, pushed tree before any run; repo-wide `git status`/`git diff` plus `git reflog`/`git stash list` after; stage by explicit path only.
3. Don't assume the formal design-system picker is what applied a palette to a folder-linked project's output — verify from the project's own DB record and the agent's message trace if precision matters; the agent may find and use project-adjacent files on its own. ⟲ *Corollary 2026-07-29:* conversely, **do** set the picker — it is the only supported channel that puts tokens in the prompt, and its absence is why the POC's success was luck.
4. Open Design's coherent role for xtty is HTML mockup exploration that gets hand-translated into SwiftUI afterward — never a path to direct Swift edits.
5. ⟲ **Turn content telemetry off before the first run of anything that reads a private repo.** Default is `content:true`, which per run ships prompt, agent output, a listing of the project folder, bash stdout, and **base64 bodies of produced files**. It is one of only two failure modes here with no rollback, and the only one with no detection either (no local send-log). The sibling is `git clean` on untracked files — which is why "clean, pushed tree before any run" is the other half of the discipline.
6. ⟲ **When a doc says a tool "isolates" or "sandboxes" something, measure the claim before relying on it.** Both safety-shaped mechanisms here inverted under measurement: `OD_SANDBOX_MODE` severs auth rather than isolating credentials, and `artifactManifest:false` gates nothing at all despite reading like a containment switch.

## Addendum 2026-07-29 — project creation is scriptable (the GUI-only belief reversed)

> **Provenance:** 2026-07-29, produced while adding `--create-project` to `scripts/design-link.sh`. Source ground truth: `/tmp/open-design` @ `f52fda2` read directly; live verification against the installed v0.16.1 app's running daemon. A prior investigation of this question was flagged for probing the daemon's internals (raw IPC connections to mint tokens by hand, reading process env for secrets); this pass used **only** the documented first-party CLI, which mints its token internally — the method constraint is part of the finding.

### The reversal, precisely

The belief "project creation requires the GUI" rested on a true premise and a false conclusion. True: `POST /api/import/folder` over HTTP **is** gated — re-measured first-hand this pass, a tokenless POST returns `403 {"error":{"code":"FORBIDDEN","message":"desktop import token rejected","details":{"reason":"token missing"}}}` and creates nothing. False: that the gate makes creation human-only. The installed app ships a first-party CLI subcommand that does the whole thing:

```
od project import-folder <path> [--name "<title>"] [--skill <id>] [--design-system <id>] [--json]
```

- **Where it lives:** `Contents/Resources/app/prebundled/daemon/daemon-cli.mjs`. No system `node` needed — run it through the bundled Electron helper: `ELECTRON_RUN_AS_NODE=1 "<app>/Contents/Frameworks/Open Design Helper.app/Contents/MacOS/Open Design Helper" <daemon-cli.mjs> project import-folder …`.
- **How it passes the gate:** `mintCliImportToken` (`apps/daemon/src/cli.ts:6975`) sends `MINT_IMPORT_TOKEN` for the target `baseDir` over the daemon's IPC socket read from `OD_SIDECAR_IPC_PATH`, and attaches the result as `x-od-desktop-import-token`. The gate is **satisfied, never bypassed** — the token is minted by the daemon itself.
- **The env it needs:** without `OD_SIDECAR_IPC_PATH` the CLI both mints no token **and** resolves the daemon URL to a wrong default (`daemon-url.ts`: flag → `OD_DAEMON_URL` → IPC STATUS roundtrip → dev-tools probe → hardcoded `http://127.0.0.1:7456`, while the real daemon binds an ephemeral port). The socket path is discoverable from public process metadata alone: the daemon's own `--od-stamp-ipc=<path>` argument (via `ps`), its `OD_SIDECAR_IPC_PATH` env, or the deterministic default `/tmp/open-design/ipc/<namespace>/daemon.sock`.
- **What the route stamps:** `metadata = {kind:"prototype", baseDir:<realpath>, importedFrom:"folder", entryFile, fromTrustedPicker:true}` (`import-export-routes.ts:395-410`) — the same folder-backed shape the GUI picker produces, with `baseDir` canonicalized through `realpath` at import.

**The semantic cost, stated plainly:** `fromTrustedPicker: true` is stamped for *any* valid token (`import-export-routes.ts:301-322` verifies HMAC+path+nonce, nothing about origin). While creation was GUI-only the flag genuinely meant "a human chose this folder in the native picker"; with creation scripted it means "a valid HMAC was presented". The owner accepted this knowingly; it is recorded in `design/README.md` so the flag is never read back as an audit trail of human consent.

### Two operational hazards (both measured 2026-07-29)

1. **No dedupe on folder import.** The import route has no existing-project check and the `projects` table constrains only `id` — not `name`, not `metadata.baseDir` (`db.ts:58-67`). Re-importing the same directory creates a second independent project at the same folder, each with its own design-system setting; a run in the unconfigured one silently skips the tokens. Observed live via a double-fired GUI click. Consequence: any scripted creation must dedupe by `realpath(metadata.baseDir)` *before* creating (names are not identity), which is exactly what `design-link.sh --create-project` and its `--status` duplicate advisory do.
2. **API/CLI project deletion leaves a phantom card in the app's UI** that the in-app "Refresh" button does **not** clear — only quitting and relaunching does (DB and disk had one project while the UI showed two). Delete projects in the app, or expect to relaunch after an API delete. (Deletion itself is clean at the data layer: the row is gone on re-GET and `baseDir` content is untouched.)

### Reusable guidelines (continuing this doc's numbering)

7. **Before declaring a gated HTTP route "human-only", inventory the vendor's own CLI surface** — a first-party tool that mints the gate's credentials internally is the sanctioned scripting path, and using it keeps the gate's integrity (never hand-mint tokens or read secrets from process state; if the CLI route fails, fall back to documented manual steps, not a workaround).

## Addendum 2026-07-29 (b) — teardown symmetry: the workspace copy is a project row, and the project-delete route is the safe one

> **Provenance:** 2026-07-29, produced while making `scripts/design-link.sh --uninstall` undo everything `--install` now sets up. Ground truth: `/tmp/open-design` @ `f52fda2` read directly; live verification against the installed v0.16.1 app — first through a throwaway git repo under `/tmp` driven through the same script code path, then a real `make design-unlink` → `make design-link` round-trip.

### The `ds-<pkg>` workspace copy is a full project row, not just a directory

The frozen-DESIGN.md workspace this doc's freeze remedy targets (`rm -rf …/data/projects/ds-xtty/`) is only half the object. `ensureUserDesignSystemWorkspaceProject` (`apps/daemon/src/design-systems/server-services.ts:226-270`) **upserts a project row** — id from the design system's stamped `projectId` if safe, else `ds-<dirId>` (`:230`) — with metadata `{kind:"other", importedFrom:"design-system", entryFile:"DESIGN.md"}` and **no `baseDir`**, then copies the package files into `<data>/projects/<id>/`. Two consequences:

- The `projectId` the daemon writes back into the repo's `design/xtty/metadata.json` is the **workspace project's id** (`ds-xtty`), not the mockups project's UUID — so it is stable across teardown/re-link and the committed value never goes stale.
- The freeze remedy (`rm -rf` of the dir alone) still works — the row is *upserted* on next picker use, dir re-copied — but it is not a clean-slate teardown: the row survives as residue. Complete removal is the ungated `DELETE /api/projects/ds-<pkg>`, which removes row **and** dir in one app-sanctioned move.

### The two delete routes have opposite safety profiles — name them precisely

- **Design-system delete** (`DELETE /api/design-systems/user:<id>` → `rm(path,{recursive:true,force:false})`, `index.ts:1451-1460`): still **banned** — whether it unlinks the symlink or recurses into the repo working tree remains deliberately unverified. Teardown removes the symlink by hand, `unlink(2)` only.
- **Project delete** (`DELETE /api/projects/:id`, `routes/project/index.ts:2273-2288`): **safe and now used by teardown.** It cancels owned runs, deletes the row, then `removeProjectDir` — which resolves only `<data>/projects/<id>` and **never** `metadata.baseDir` (`projects.ts:1339-1342`). Proven live, not just read: `git status --porcelain design/` (and an md5 over the tree) byte-identical across a real delete of the folder-backed mockups project. The bundled CLI's `od project delete` is a bare unauthenticated `fetch` of this same route (`cli.ts:6220-6230`) — so plain `curl` is the same mechanism; the Electron-helper + IPC ceremony is only ever needed to mint the *import* token.
- The route is **forgiving to the point of being evidence-free**: it returns `{ok:true}` when only the dir exists (row long gone), and when *neither* exists (`dbDeleteProject` no-op + `rm force:true`). A 200 from it proves nothing — verify by re-`GET /api/projects`.

### What even the app's own delete leaves behind

Run history lives at `<data>/runs/<runId>/` keyed by run id, with `state.json` carrying the owning `projectId`; project deletion does not touch it. Observed live: run dirs referencing project ids that no longer exist in the DB (including pre-POC GUI-deleted projects) — so "delete the project in the app" never was a full clean slate either. `--uninstall` reports the count of orphaned run dirs rather than deleting them (they are app-side only and reference nothing in the repo).

## Addendum 2026-07-29 (d) — the package directory's basename IS the design-system id: renaming `design/xtty/` → `design/design-system/`

> **Provenance:** 2026-07-29, produced while renaming the committed package directory to `design/design-system/` (owner readability call — the tree now reads `design/design-system/` + `design/mockups/`). Ground truth: the pinned `f52fda2` clone at `/tmp/open-design-src`, read directly (ref re-verified before reading); live verification against the installed v0.16.1 app — a throwaway `/tmp` git repo driven through the edited script's own code path first, then the real teardown → rename → re-link, a sentinel generation run, and a full `make design-unlink` → `make design-link` round-trip.

### The id is underivable from anything but the path — so a directory rename is an id migration

✅ **No install-time id channel exists.** `POST /api/design-systems/install` accepts exactly `{source:"github", url}` or `{source:"local", path}` (`installFromTarget`, `library-install.ts:62-72`) — no id, no name field. The local arm symlinks at `<data>/design-systems/<basename(realpathSync.native(path))>` (`installFromLocal`, `:133-181`; basename at `:162`, symlink at `:175-180`), and the catalog id is minted on every list as `user:` + the bare readdir entry name (`listDesignSystems`, `design-systems/index.ts:269-310`; id at `:310`). Nothing in `metadata.json` or `manifest.json` can override it — so renaming the package directory *is* renaming the design-system id: `user:xtty` → **`user:design-system`**. Keeping the old id was considered and rejected: it would need a hand-minted symlink named `xtty` pointing at the renamed directory — a shape no documented route produces, which the script's repair state machine (keyed on `<data>/design-systems/<basename>`) would never see, while any later install/repair minted a second entry `user:design-system` beside the orphan. The id is not user-facing (the picker shows the *title*, `metadata.title` = `xtty`), so nothing readable was lost.

⚠️ **`manifest.json.id` must equal the new basename, or the whole manifest silently vanishes.** `readProjectManifest(brandRoot, expectedId)` validates `record.id === expectedId` where `expectedId` is the directory entry name (`isProjectManifest`, `design-systems/index.ts:3683-3702`) — on mismatch it returns `null` with no warning anywhere, and the catalog falls back for title/category/summary (costing the picker subtitle, which is the manifest `description`). Proven by effect after the fix: the catalog entry's `summary` re-read as the manifest description verbatim.

⚠️ **The committed `projectId` write-back pins forever — a rename strands it; drop the key, never hand-rewrite it.** `projectBackedDesignSystemProjectId` *prefers* a safe recorded `metadata.projectId` over deriving `ds-<basename>` (`design-systems/server-services.ts:233-238`), so with `"projectId": "ds-xtty"` still committed, every workspace ensure after the rename would have reused `ds-xtty` — permanently divergent from the `ds-<pkg>` id that the script's teardown (`DELETE /api/projects/ds-$PKG_NAME`) and the freeze remedy (`rm -rf …/projects/ds-<pkg>`) both compute, i.e. a standing orphan. ⟲ This **narrows addendum (b)'s claim** that the committed write-back "is stable across teardown/re-link and never goes stale": that stability holds *only while the basename is unchanged* — the value is stable *because* it is pinned, and the same pinning makes it wrong after a rename. Remedy, in the rename commit: delete the stale key (the one hand-edit; it removed a pointer to a row that no longer existed — the daemon-side rows had been torn down first) and let the app re-mint — `POST /api/design-systems/user:design-system/workspace` (the same `ensureUserDesignSystemWorkspaceProject` the picker/generation path runs, `server.ts:3893`; exposed at `routes/design-systems.ts:277`) returned 201 and `linkUserDesignSystemProject` (`design-systems/index.ts:1315-1342`) wrote `"projectId": "ds-design-system"` back through the symlink, all authored keys preserved; that one-line diff was committed deliberately.

✅ **Ordering: tear down the old id in full *before* `git mv`.** The script derives everything (`DS_ID`, the link path, `ds-<pkg>`) from the basename, so after a rename it can no longer name the old artifacts — teardown-after-rename would compute the new id and leave the `xtty` symlink dangling plus any `ds-xtty` row/dir orphaned. Sequence used: `make design-unlink` (old id; verified orphan-free from the daemon and filesystem) → `git mv` → reconcile the identity-coupled files → `/tmp` rehearsal → real `make design-link` → workspace-ensure write-back.

⚠️ **A generic basename occupies a machine-global name.** `<data>/design-systems/` is flat and keyed by basename, so any other repo installing a package directory also named `design-system` collides. The failure is loud, not silent — the install route 400s `already installed "design-system"` and creates nothing (`installFromLocal`'s collision check, `library-install.ts:164-171`). Accepted for the readability win.

## Addendum 2026-07-29 (i) — model selection: a global per-agent config key, scripted through the GUI's own route; the tier aliases outlive the app's pinned list

> **Provenance:** 2026-07-29, prompted by an owner request to match the model to the job (cheap to iterate, strong to author a baseline) and to make the pick reproducible. ✅ **Resolution order at spawn (`server.ts:4925-4936`).** Per-request `model` field → `agentModels.<agentId>.model` from app-config → `"default"`. A value `isKnownModel` recognizes passes verbatim; anything else goes through `sanitizeCustomModel` (`models.ts:205`: `^[A-Za-z0-9][A-Za-z0-9._/:@-]*$`, ≤200 chars) and is passed through if it matches. `resolveModelForAgent` (`:175-197`) returns a non-`default` resolved value unchanged, so a custom id reaches the CLI as `--model <id>` intact. For the `claude` runtime there is **no env-var lever** — the def declares no `defaultModelEnvVar` — so the request field and the config key are the only two.

✅ **`"default"` means no flag at all, not a model.** `buildArgs` pushes `--model` only when `options.model && options.model !== 'default'` (`defs/claude.ts:66-68`). The out-of-the-box state is therefore *the agent CLI's own configured model*, with Open Design expressing no opinion.

❌ **"Open Design was defaulting us to Sonnet" — refuted by the GUI drive.** The stored config had no `agentModels` key at all and the dropdown read `Default (CLI config)`; the Sonnet in use came from the local `claude` CLI's own configuration. The app was not choosing a model; it was declining to.

✅ **The write is one additive key, captured by driving the real picker.** Selecting `Opus (alias)` in the composer chip → Model dropdown wrote exactly `"agentModels": {"claude": {"model": "opus"}}` — a whole-config diff before/after showed nothing else moved, `telemetry.content` still `false`. That observed shape is what the script reproduces; it was not guessed from the type definition.

✅ **`PUT /api/app-config` is a whole-config replace, not a merge** (`routes/media.ts:485` → `writeAppConfig(RUNTIME_DATA_DIR, req.body)`). A partial PUT would silently drop every unsent key — including `telemetry.content: false`, the one value here with a safety consequence (default-on content telemetry ships file bodies to a remote relay). The script therefore always read-modify-writes the full object and asserts `content === false` on every write, failing loudly otherwise. Origin gating (`isLocalSameOrigin`) admits a local non-browser client: curl sends `Host: 127.0.0.1:<port>` and no `Origin`, which `isAllowedBrowserHost` accepts (`origin-validation.ts:212-243`).

✅ **Config normalization does not validate the model string.** `normalizeRetiredAgentPrefs` (`app-config.ts:449-478`) only drops entries for retired agent ids; any model string survives the write and is adjudicated later at spawn. Hence the script validates against the daemon's own regex at set time — otherwise a malformed id would store cleanly and then silently no-op at spawn, which reads as "the setting did nothing".

✅ **Scripted writes appear in the GUI live, with no restart** — re-opening the chip after a scripted set showed the new value in both the header line and the dropdown. Conversely a direct file poke is the wrong mechanism: the daemon holds app-config in memory and fires `onAppConfigWritten` hooks, so a file write is ignored until relaunch and is overwritten by the next GUI action.

✅ **Prefer tier aliases over pinned ids.** `CLAUDE_FALLBACK_MODELS` (`defs/claude.ts:6-14`) offers `default` + `sonnet`/`opus`/`haiku` aliases + pinned `claude-{opus,sonnet,haiku}-4-5`. The aliases resolve inside the agent CLI at spawn, so they track the current model of each tier; the pinned ids are 4.x-era and predate Claude 5 entirely. Local `claude` 2.1.220 accepts both `fable` and `claude-fable-5`; an unknown id is rejected by the CLI with a readable message and **exit code 0**, so an exit-status check is not a valid model probe.

### Reusable guidelines (continuing this doc's numbering)

18. **A "default" setting may mean *no opinion expressed*, not *a default value chosen* — check whether the flag is emitted at all before attributing behavior to the tool.** The visible symptom (runs using Sonnet) was produced entirely outside the tool being blamed; the tool's stored state was empty and its code path omitted the flag.
19. **Before scripting a settings write, drive the real UI once and diff the store.** The observed write here was one additive key; a type definition would have suggested several plausible shapes, and a wrong guess against a whole-config-replace route silently destroys unrelated settings.
20. **When a config route replaces rather than merges, treat every unsent key as deleted — and assert the safety-relevant ones after each write.** Read-modify-write is necessary but not sufficient; the post-write assertion is what catches a merge bug before it becomes a silent privacy regression.
