### 2026-07-28 — Open Design integration for xtty UI drafting (research capture, not an OpenSpec change; investigation + hands-on POC)

The owner asked what could be done with Open Design (nexu-io/open-design, an "agent-native, local-first" design tool, already brew-installed) for xtty, then specifically to try using it to draft new xtty UI directions, starting from a "design base" derived from the already-implemented app. Investigated across three staged Workflows (a Fable-plan → Opus-fan-out-8-angles → Fable-audit landscape pass; two Fable investigate→scrutinize passes on design-base feasibility and app setup) plus a hands-on POC, all grounded in a real `git clone --depth 1` of the source rather than marketing copy or memory.

**Headline finding:** Open Design is mechanically stack-agnostic (its runtime is the literal `claude` CLI, spawned with `--permission-mode bypassPermissions`, which could touch any file) but productively web-only (its entire prompt/preview/export pipeline is HTML-bound, even for explicitly native briefs) — so its coherent role for xtty is HTML mockup exploration that gets hand-translated into SwiftUI afterward, never direct Swift edits. None of Open Design's three DESIGN.md-creation paths apply to a native macOS app (a live-URL brand-extractor and a CSS/JS-only importer both find nothing in a Swift tree) — the design base had to be hand-authored by reading the real source, which the POC did (`design/xtty/{manifest.json,DESIGN.md,tokens.css}`, 9 H2 sections, every claim cited `path:line`).

**A safety finding confirmed live, not just theoretically:** there is no OS-level sandbox in Open Design regardless of a project's folder scope — `OD_SANDBOX_MODE` only redirects HOME/config paths and gates which folders can be *chosen*, it doesn't restrict what a running process can actually read/write. The POC scoped its project to a small, dedicated, otherwise-empty folder (`design/mockups/`) specifically to bound blast radius rather than rely on any real boundary — and the live run proved the point: the spawned agent read a *sibling* folder (`design/xtty/`) outside its assigned project directory, unprompted, to find the design tokens. Benign here (and even helpful — the generated mockup faithfully used the real hex values and cited DESIGN.md facts directly), but concrete proof the folder boundary isn't enforced.

**One generation ran end-to-end and worked well**: a settings-pane mockup (`xtty-settings-pane.html`) correctly used xtty's real dark theme, accent-inheritance note, and status-color vocabulary — though notably via the agent's own exploratory file read rather than Open Design's formal design-system-picker field (`app.sqlite`'s `projects.design_system_id` for the run was `null`).

**Cleanup, owner decision:** the entire POC — `design/xtty/`, `design/mockups/` (including the generated mockup, never committed to git), and the installed copy at `~/Library/Application Support/Open Design/namespaces/release-stable/data/design-systems/xtty` — was wiped after this capture, for a clean-slate restart. Nothing from the POC survives elsewhere in the repo; this capture is the sole record.

Captured to `research/03-analysis/open-design-integration-forensics.md` (full depth-bar capture: mechanism, reproducible probes with a proves/doesn't-prove table, a 6-entry retired-theory fates table, re-verify-by-effect, 4 reusable guidelines, evidence pointers), indexed in `research/README.md`. One bounded Learned-refutations one-liner added to `AGENTS.md`. No OpenSpec change created (this is tooling/process exploration, not a product-milestone feature); no milestone movement.

### 2026-07-27 — fix-large-diff-memory-bound (P6 / product fix) — implemented 24/24 tasks, human-attested, archived (`git-review` +1 requirement, `verification-harness` 1 requirement modified)

**Why.** The git-review panel limited its returned model to 5,000 lines, but only *after* `GitRunner` had read the child pipe to EOF, decoded the complete `Data` into a `String`, and split it into another array of strings. ### 2026-07-20 — add-git-diff-wrap-toggle (P6 / product feature) — implemented 21/21 tasks, human-attested, archived (`git-review` spec +1 requirement, `terminal-configuration` +1 requirement, `verification-harness` +2 requirements)

**Why.** The git-review panel's diff never actually filled its ~280pt column — a `ScrollView([.vertical, .horizontal])` + `LazyVStack` + `.frame(maxWidth: .infinity)` combination collapsed content to roughly 40% of the panel width, so the P6 design's intended "horizontal scroll for long lines" never materialized. Fixing width-fill naturally splits into two legitimate behaviors — wrap vs. no-wrap — so this change ships both, in-panel-toggleable, with a config default.

**What shipped.** A `GitDiffWrap` enum + `diffWrap`/`setDiffWrap` on `GitReviewStore` (mirroring the existing `GitReviewLayout`/`setLayout`), a base-only `git-review-diff-wrap` config key, a wrap-toggle button in the diff header, and two rendering modes in `DiffPane`/`DiffLineRow`: **wrap** (new default) uses a vertical-only `ScrollView` so `Text` gets a definite width to wrap against, with continuation rows hang-indenting under the content via the existing marker/content `HStack` split; **no-wrap** keeps the two-axis scroll with every row (in a `LazyVStack`, matching wrap) floored to `max(real viewport width, a precomputed diff-wide widest-row estimate)` — the estimate computed once from character counts (no per-line text layout), so short rows still fill the panel and long rows extend the scroll, with genuine laziness preserved. A DEBUG-only `diffFillsWidth`/`diffContentOverflows` geometry signal (derived booleans, never pixels) lets an XCUITest assert each mode's actual rendered layout without measuring anything visual.

**Two bounded rounds of this change's own `/xtty:cross-review` ran against it:**

- **Round 1** (Pass A/B/C on the initial implementation): found and fixed a tautological no-wrap overflow bug — the row-width floor was applied *before* padding, so every row (even short ones) measured at least `viewportWidth + 16`, making the "overflows" signal always true regardless of actual content, silently defeating the very regression guard it existed to provide. Also unified the DEBUG/Release rendering paths (an earlier version used a DEBUG-only async `onGeometryChange`-fed viewport width that rendered a materially different tree than Release's synchronous `GeometryReader`, and silently zeroed out on pre-macOS-15 hosts); removed an incorrect `#available(macOS 15, *)` gate (the single-value `onGeometryChange` overload used is actually back-deployed to macOS 13, verified against the installed SDK's `SwiftUICore.swiftinterface`); capped no-wrap's eager rendering to 500 rows (bounding a ~15M-character worst-case main-thread layout against 5000 lines × up to 3000 chars); reset the store's geometry booleans on selection change.
- **Round 2** (Pass A/B/C re-run against round 1's fixes): found round 1's own 500-row cap had introduced a **more serious defect** — toggling wrap→no-wrap on a diff over 500 rows silently dropped rows that wrap mode still showed, violating the "switching modes never changes which lines are shown" invariant (Codex Pass B, high; independently corroborated by Fable Pass C tracing the same defect to a now-inaccurate spec-delta SHALL). ### 2026-07-12 — cross-review archive gate: defects found by *using* it (research capture; the check-(4a) deletion + range-pollution fixes **not yet proposed**)

**What happened.** One day after `add-cross-model-design-review` archived, its gate was **used** on the next real change — and the first use surfaced defects that ~16 rounds of adversarial *spec* review had not. This is **G-TARPIT-4 in action**, and it is the strongest evidence yet for that guideline: *a dev tool is validated by building and using it, not by reviewing its spec.* Full forensics (mechanism, probes, fates, guidelines **G-GATE-1..5**): `research/03-analysis/cross-review-gate-defect-forensics.md`. Everything below was **measured by effect** against the real committed scripts in throwaway repos; the live repo was never mutated.

**The route in.** A `/xtty:cross-review` launch on `add-git-diff-wrap-toggle` was aborted at step 0 when its reviewed range turned out to be **~80% foreign** (the positional base swallows every commit landed since the change was parked). Investigating *that* produced the rest.

**The findings.** **(1) A re-attestation deadlock.** Once post-attestation drift invalidates check (2), *every* forward-history way to record a fresh attestation fails check (4)'s counter — modify-in-place and delete+re-add give `adds=2 dels=1`, appending a second line gives `now=2`, and `git revert` leaves `dels=1` forever. The only escape is a **history rewrite**, while the spec's own fail-closed scenario *mandates* "a fresh review and attestation". This was **already known** — the archived change's own ledger carries it as finding **rB1** (HIGH, raised by `gpt-5.6-sol`) and dismissed it with a recovery (*"rewrite the local pre-archive attestation commit"*) whose gesture is **byte-for-byte the attack in (2)**. **(2) That counter is adversarially *null*, as specified.** Three forgeries pass **all four checks** on content the human never saw: reset-laundering; amend-forge; and the decisive **split-commit forward forge** — edit the reviewed file in commit A, write the attestation in commit B, **two plain forward commits, zero history rewriting**. **(3) ⚠️ But check (4)'s *confinement clause* is genuinely load-bearing, and separable.** An `--amend` bundle (commit the task text → compute the digest → amend the attestation into that commit) passes checks 1–3 **and** the counter; **only confinement catches it**. So the operative fix is **delete the counter (4a), preserve the confinement clause (4b)** — narrower than what the co-research converged on. **(4) The scope classifier is retrospective.** It scopes from *committed* paths, so before a change's implementation lands it returns a confident **false negative** (`exit 0`, "out of scope"), **not** an abstention — only `exit 10` is positively informative, and `exit 2` conflates four distinct causes. **(5) ⚠️ A verified bypass.** With the implementation merely **uncommitted**, the classifier reads `exit 0`, so AGENTS.md step-0 (which applies *"for a change in scope"*) skips the **entire** four-check precondition and `openspec archive` proceeds. The counterintuitive part: the digest's dirty-tree refusal **cannot** backstop this — it *is* check (3), **inside** the precondition that was skipped. **(6) Range pollution** is HEAD-dependent (any commit anywhere restages a digest), corrupts the *scope classifier* too (`add-git-diff-wrap-toggle` classifies in-scope on 8 paths that are **all foreign** while its own 7 are 100% allowlisted), hashes a *foreign archived* ledger into the digest, and has **no metadata-free fix** — but it is **fail-closed**, so it is noise, not a hole.

**The sharpest lesson, and it lands on our own process.** Check (4)'s counter was **added** one day earlier (commit `3319785`, tar-pit §11) by a **net-smaller, two-model-agreed, floor-compliant** co-draft that both models judged to be closing a real gap. It closed nothing — and it bricked the honest path. **A content floor and cross-model agreement bound *bloat*, not *wrongness*.** §11's hardening was itself the tar-pit relapse its own doc warns about (recorded as a **§12 addendum** there, append-only).

**How it was worked.** A bounded co-research Workflow (`wf_9af3679c-537`: Fable-5 ‖ `gpt-5.6-sol` ‖ Opus adjudicator, **converged in 3 rounds**) plus an adversarial verification fan-out (`wf_cfbf0992-20b`, 9 agents), then a live tri-pass `/xtty:cross-review` of the follow-on change `fix-cross-review-gate-task-emission` (2 bounded rounds; ledger committed at `openspec/changes/fix-cross-review-gate-task-emission/cross-review-ledger.md`, findings **F1–F12 / G1–G11**). Notable process honesty: **Fable-5 built a drill that refuted its own proposal and withdrew it**; the adjudicator (me) **over-promoted a low-severity note into a load-bearing Decision and was refuted by its own probe**; and **`gpt-5.6-sol`'s sandbox blocked `mktemp`**, so it never ran a drill — the *analytic* cross-model consensus is genuine, but the **empirical leg is single-runner**, and the doc says so rather than overselling it.

**Status — nothing shipped; the check-(4) fix is NOT settled; and a FOURTH round found the deepest defect yet.** After three cross-review rounds, a **fully-informed** Codex run (given the brief + the drill results its **read-only sandbox** can never produce — `mktemp` fails) found what three uninformed runs and every in-house pass had missed. **(a) There is no executable archive gate at all:** the archive skill has **zero** references to cross-review/attestation/step-0; `exempt_by_act()` lives only in a *test harness*; the digest tool prints a value but **nothing committed compares it or refuses archive**. *"Fail-closed" is an instruction-following convention, not an enforced property* — **not running step-0 bypasses everything, undetected.** **(b) Every drill measured only the *executable* fragment.** The specified clause **4c independently blocks the honest recovery** (verified: check (2) **green**, 4a **red**, **4c red**), so *"delete the counter ⇒ liveness restored"* — the premise under **every** prescription — is **false**; and *"4c is redundant with check (2)"* is refuted. **A model that cannot run a single drill caught this by reading the spec, because I had been measuring what I could execute rather than what was specified.** **(c) The tension is formally irreducible** for a gate observing only model-writable git state: *human review is an event in the world, not a property encoded by git*. The only exit is an **externally authenticated human act** — the repo's own already-declined optional signing form. **The design cannot keep both liveness and silent-re-attestation prevention without an external authority.** **(d) A taxonomy contradiction:** the silent re-attestation is a model performing the **forbidden human-only act** (already accepted as the **R3** residual), yet the capture had reclassified it as *"the principal ordinary accident"* — intent is no more git-observable than review. ### 2026-07-10 — scroll-reversal redraw corruption: root cause found (research capture addendum, same-day follow-up)

A same-day follow-up investigation (still `/opsx:explore`, no product code touched) closed every `❓` the original capture left open, via a live interactive session against the running Debug build plus two `/xtty:research` Workflow fan-outs.

**Live re-characterization (via `peekaboo` driving the real app, delivery confirmed each time through the DEBUG `lastWheelRouting` telemetry, never trusting a CLI's own success message):** momentum is not required — a plain discrete, non-precise tick reproduces the corruption identically to a real trackpad flick. Depth is not required — the *shallowest possible* reversal (one wheel tick down, one tick up — 5 SGR reports each direction after xtty's own quantization) corrupts from a clean baseline. It is fully deterministic — the identical minimal sequence produces byte-for-byte identical garbled text every run. A window resize that changes the actual character grid (crossing a real cell-size boundary, so htop gets a genuine `SIGWINCH`) heals it completely and instantly; a resize that doesn't change rows/cols does nothing — this became the decisive **model-vs-render discriminator** (a sub-cell resize forces the CoreGraphics view to fully redraw from the *same* wrong model without healing, proving the corruption lives in the `Terminal` model, not the renderer). A related glitch was found on terminal-width-shrink in the CPU-meter-bar area (same "survives repeated live redraws" signature), and one frame showed a full row (`configd`) duplicated at two physical positions.

**The mechanism hunt itself had a genuine wrong turn, caught and corrected.** A first `/xtty:research` fan-out (ncurses + SwiftTerm scroll-region readers → synthesis → adversarial critic → a bare-`pty.fork()` verify-by-effect) measured **zero** scroll-region-shift sequences in 80 captured htop redraw ticks — only `VPA`+`DCH`+`EL` — and concluded SwiftTerm's `cmdScrollUp`/`cmdScrollDown` were irrelevant. That measurement was honest but of the wrong regime: a later check found htop's process list had **never actually scrolled** in that bare-pty harness (content stayed byte-identical across 60+ ticks despite htop visibly reacting) — a mouse-coordinate/focus-calibration gap in driving bare htop outside the real app. This is now recorded as **guideline G(verify-the-regime)**: a verify-by-effect probe returning a clean/negative result must confirm it actually reached the state under test, not just that it sent input and got some reaction back.

**The real breakthrough:** captured genuine PTY bytes from the *live, already-reproducing* xtty app (relaunching htop wrapped in `script -q` inside the running session — a transparent tap, no code changes) during the proven minimal-reversal recipe, then replayed those exact bytes through a headless SwiftTerm `Terminal` (the `NoopTerminalDelegate` pattern already used in `XttyCore/Tests/XttyCoreTests/TerminalSessionTests.swift`). **Byte-for-byte identical corruption reproduced, with zero xtty-app involvement** — proving the defect is 100% in upstream SwiftTerm's parser. Grepping the real capture showed htop genuinely *does* use `DECSTBM`+`SU`/`SD` (scroll-region hardware-scroll) for real list-scrolling — the earlier "no scroll-region ops" finding is retracted — and bisection pinned the corruption's first appearance to immediately after the first SD op following a run of SU ops (the real direction-reversal point).

**Root cause, confirmed from source and numerically verified:** `cmdScrollDown` (SwiftTerm `Terminal.swift:4646`, handles `CSI Ps T`/SD — invoked scrolling back toward the top of htop's list) is missing the `if marginMode {…} else {…}` guard its sibling `cmdScrollUp` (`Terminal.swift:4672`) has — it always computes `columnCount = buffer.marginRight - buffer.marginLeft + 1` and does a narrow margin-bounded copy, with no full-width fallback when column-margin-mode is off (the normal case; htop never enables DECLRMM). Traced fully: neither `Buffer.init` (`Buffer.swift:273`) nor `activateAltBuffer` (`Terminal.swift:789`, which creates htop's alt-screen buffer) ever sets `marginLeft`/`marginRight`, so they sit at their raw defaults (`0`/`0`) — giving `columnCount = 1`. Every scroll-down shifts *only column 0*, leaving every other column frozen indefinitely — unifying both symptom classes (trailing garbage columns never touched; row duplication because the old physical row's untouched columns keep showing stale content while htop explicitly redraws the new position) under one cause, not two.

Captured as a dated addendum (§7, not a rewrite) to `research/03-analysis/scroll-reversal-redraw-corruption-forensics.md` — new fates-table rows T8–T12 (including the retracted-then-reinstated T9), reproducible probes (the mouse-position gotcha for `peekaboo`, the resize-heal recipe, the real-capture-and-replay recipe), a source-level re-verify, and guideline `G(verify-the-regime)`. `research/README.md`, this file's `AGENTS.md` table-row one-liner, and `packer/README.md`'s expected-difference matrix row all updated to reflect the found root cause. **Still not yet an OpenSpec change** — the diagnosis is settled; a fix proposal (mirroring `cmdScrollUp`'s guard onto `cmdScrollDown`) has not been drafted.

### 2026-07-09 — fix-scroll-wheel-mouse-reporting (P-tooling / product fix) — implemented 15/15, manual-verified by effect + full matrix `47/0/1` of 48, archived

**The bug:** full-screen apps that enable mouse tracking (htop, vim, tmux, fzf, less-with-mouse) **did not scroll with the mouse wheel** in xtty. Root cause (from the `mouse-wheel-scroll-forensics.md` research): xtty's embedded SwiftTerm `MacTerminalView.scrollWheel(with:)` unconditionally moved its own local scrollback and **never read `terminal.mouseMode`**, emitting **zero pty bytes** on the wheel; on the alternate screen that local scroll is a dead no-op (`maxScrollback = 0`). iTerm2 on identical input scrolls htop a full page.

**What shipped (product fix, via the SwiftTerm patch):** `scrollWheel(with:)` rewritten as the priority-ordered **3-way branch** every mature terminal converges on — (1) **mouse reporting active** (`allowMouseReporting && terminal.mouseMode.sendButtonPress()`, i.e. vt200/buttonEventTracking/anyEvent; excludes off/x10) → a **wheel mouse-report** via `encodeButton(button: up ? 4 : 5, …)` (SGR 64/65) → `sendEvent`, press-only, at the `calculateMouseHit` pointer cell (0-based col, `yDisp`-clamped row); (2) **alternate screen, mouse off** → cursor **Up/Down keys**, DECCKM-aware (`terminal.applicationCursor` selecting SS3 `ESC O A/B` vs CSI `ESC [ A/B`); (3) **primary, mouse off** → the existing local scrollback (unchanged). Plus the **Shift-bypass** (Shift-modified wheel → local scrollback even under mouse reporting), the `deltaY == 0` horizontal guard, momentum collapse (`momentumPhase != []` dropped), and a bounded per-event row count (`xttyWheelRowCount`, NOT `calcScrollingVelocity`-as-count which floods 20–32/notch). Delivered as a hunk in `patches/swiftterm/xtty-accessors.diff` (regenerated from the checkout), upstream-ready. **Observability:** a `lastWheelRouting` DEBUG state-dump field (branch + direction + count + button/keyForm), backed by a new `public struct XttyWheelRouting` in `XttyAccessors.swift` (xtty-local, demarcated for stripping when the fix lands upstream). **TN3179 read in full (macOS considerations).** The `AllowedEthernet/WiFiLocalNetworkAddresses` keys are a **destination-address exemption** ("treats every address on that network as if it were not a local network address … Every program can access that address") — they gate *connections to addresses*, orthogonal to xtty's reverse-DNS *query* trigger, so they can't cover it. ## Build-infrastructure history (formerly AGENTS.md → Building, full original bullets)

- **Metal Toolchain (one-time):** SwiftTerm bundles a `.metal` shader, so even though we don't use its renderer yet, the build compiles it. On Xcode 26+ the Metal compiler is a separate component — install it once with `sudo xcodebuild -downloadComponent MetalToolchain` (or Xcode → Settings → Components) or the build fails with `cannot execute tool 'metal'`. **Cleanup PROPOSED as `retire-metal-renderer` (2026-07-04 — `local-macos-vm-ci-reproduction.md` §10b/§11g):** this dependency exists *only* because SwiftTerm declares the shader as `.process("Apple/Metal/Shaders.metal")` (Package.swift:83); patching that out via the existing `patches/swiftterm/xtty-accessors.diff` makes xtty build with **zero Metal toolchain** — dropping the fragile `xcrun -f metal || sudo xcodebuild -downloadComponent MetalToolchain` guard from CI (the Metal download is a deterministic Apple-catalog-rotation trap, not flakiness) and aligning with the P7b keep-CoreGraphics decision. Cost: the Metal e2e arm (`testConfiguredMetalRendererIsReported`) is deleted — its behavior no longer exists. A lean **~38–40 GB golden-clone VM image** (macOS + Xcode-no-simulators, Metal patched out) is the researched minimal reusable test rig — see §10; the reproducible Packer-template version (§11) is now a **real target** — see the next bullet + `packer/README.md` (the `add-xtty-test-image` change; hard dependency: `retire-metal-renderer` first).

- **Local VM test image (optional):** `make image` builds the minimal **~40 GB** Tart image `xtty-test:26.5` from pinned inputs (`packer/xtty-test.pkr.hcl` — a cirruslabs `macos-tahoe-base` **digest** pin + Xcode 26.5 installed from a pre-downloaded official `.xip` + XcodeGen; **no simulators, no Metal toolchain, no xtty source baked in** — the repo arrives at test time in a disposable clone). Purpose: run the full suite incl. XCUITests in a local CI-parity VM — the per-launch race class reproduces at 3 vCPU in a VM, not on bare metal. Prereqs are **human-gated** and only advised by the target (`brew install packer`; a one-time Apple-ID `xcodes download 26.5` → `~/XcodesCache/`; `TART_HOME` on a volume with ~85 GB free). **Depends on `retire-metal-renderer`** (the zero-Metal build). Golden-clone runtime workflow, Metal-absence verification, pre-registered acceptance envelope, and maintenance: **`packer/README.md`**.

- **Optional stable local signing (dev convenience):** ad-hoc signing changes the app's code identity every rebuild, so any TCC grant (notably **Screen Recording**, which `make bench`'s latency probe needs) re-prompts on each build. To make a grant persist, create a self-signed code-signing cert once with **`scripts/create-signing-cert.sh`** (→ `xtty-dev`) and build with **`XTTY_SIGN_IDENTITY=xtty-dev make build|test|bench`**; unset, builds stay ad-hoc/portable (CI + other contributors unaffected). This is the lightweight slice of the deferred P7-distribution signing work — *not* Developer ID/notarization. Formalized as the **`add-local-signing-identity`** OpenSpec change (a `build-workflow` spec delta). Details + the experiment write-up: `research/03-analysis/p7-measurement-methodology.md` (2026-06-29 addendum). The **full distribution** (Developer ID + Hardened Runtime + notarization) is researched in `research/03-analysis/distribution-signing-research.md` (2026-06-30) — **technically green, gated only on a ~$99/yr Apple Developer Program decision**: the HR-exception entitlement set is empty (HR doesn't break exec'ing unsigned user binaries — child processes get independent AMFI evaluation), nothing xtty built breaks (one build-config change, not code), recommended change `add-distribution-signing`; captured, not yet proposed.
