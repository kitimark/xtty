## Context

`fix-scroll-reversal-redraw-corruption` (concurrently open) fixes a real SwiftTerm defect. Its regression test was drafted twice: first mirroring an existing real-program end-to-end test (`testWheelScrollsRealMouseTrackingPager`, which drives real `less --mouse`), then rewritten after investigation found that approach doesn't work for this specific defect — `vim` and `less` (the programs bundled in the test VM) never invoke the buggy `cmdScrollDown` at all regardless of how they're driven (`vim` uses already-guarded `IL`/`DL`; `less` uses a bare `RI` with no scroll region), while `htop` (which does hit it, via ncurses' own hardware-scroll optimizer) is brew-only and absent from the VM image. A real-program test there would have passed green while proving nothing.

A same-session `/opsx:explore` → `/xtty:research` fan-out (readers → synthesis → adversarial critic → verify-by-effect) investigated four threads this near-miss raised: whether a manual verify task should be added to close a real-htop confirmation gap, how to word a durable rule capturing the lesson, where that rule should live operationally, and whether existing tests carry the same latent shape. Findings below are load-bearing for this change's scope.

## Goals / Non-Goals

**Goals:**
- Capture the "match test precision to the claim" lesson as an authoritative `AGENTS.md` rule, worded so it cannot collapse into a simplistic "always prefer low-level/synthetic tests" misreading.
- Give the `xtty-openspec-critic` agent a concrete way to ask the question during review, at the correct severity (REVIEW, not BLOCKER — it is a semantic judgment call, not a mechanical gate).

**Non-Goals:**
- Adding a manual verify task to `fix-scroll-reversal-redraw-corruption`. Investigated and rejected (D1) — the causal chain is already fully closed by existing evidence from this session; a manual re-run would be ceremony, not new information. That change's own scope is unaffected by this one.
- Auditing or fixing any existing test found during the research pass. The audit (7 files checked: the original 6 plus `XttyMouseWheelUITests.swift`, independently re-verified) came back clean — one soft candidate (`tput smcup`/`rmcup` in `XttySemanticCaptureUITests.swift`) was confirmed twice over to be a false alarm (`smcup`/`rmcup` is the universal alt-screen entry point, the inverse of `cmdScrollDown`'s narrow bug surface). Two suites (find-bar, multiplexing) remain unaudited — named here as a known, open residual, not silently dropped, but not this change's job to close.
- A `config.yaml` `rules.tasks` marker, or a new `design.md` template section. Both considered and rejected (D2).

## Decisions

**D1 — No manual-verify task for `fix-scroll-reversal-redraw-corruption`.** An adversarial critique of the research synthesis found the full causal chain already closed by primary evidence gathered earlier in the same session: (a) real htop's byte emission (`DECSTBM`+`SU`/`SD`) was confirmed via a byte-exact capture replayed through a headless `Terminal`; (b) the *unfixed* corruption was already reproduced live on a real, running htop (`smooth-scroll-wheel-momentum` task 4.4, step (e)); (c) the fixed code's handling of those exact bytes is proven by `fix-scroll-reversal-redraw-corruption`'s own printf-driven test. ncurses emits the same `SU`/`SD` bytes regardless of whether xtty renders them correctly — there is no feedback path from "render was wrong" back into "htop emits differently" — so a post-fix manual htop run would add no causal link the synthetic test misses. A follow-up verify-by-effect pass independently confirmed the bug is *p*-independent (the shift loop repeats the same column-limited copy regardless of scroll count), closing the one theoretical gap (a multi-line `SD` not covered by the test's `p=1` case) that might have justified a manual re-check.
   - *Alternative considered:* add it anyway as cheap corroboration, non-archive-gating. Rejected — `design.md`'s own D3 in that change already explicitly scoped out real-program coverage as "not currently planned"; adding a manual task here would mildly relitigate a decision that change already closed on its own merits.

**D2 — Operationalize as one `AGENTS.md` bullet + one `xtty-openspec-critic` Pass-1 heuristic line; no `config.yaml` marker, no new template section.** Reasoning, grounded in reading the actual mechanisms rather than assumption:
   - The 4 existing `config.yaml` `rules.tasks` entries are all *procedural delegation triggers* — a point-of-tick signal that must survive into a task line because `/opsx:apply` does not re-read `AGENTS.md` and needs an external hand-off cue (spawn an agent, run the archive ritual). This rule has no such downstream mechanical consumer: it is a one-time design-time judgment made by whoever authors the test, before any task executes. It is reasoning content, not a dispatch signal — a marker would fire only after the test-design decision is already made, and would add to the "diminishing returns from an ever-growing rules list" concern already visible in the existing 4 entries.
   - No `design.md` template section has ever been added (the standing sections are Context/Goals-NonGoals/Decisions/Risks/Migration/Open-Questions), and this concern already has a natural home: two archived changes (`split-shell-dependent-testplan` D2; `fix-scroll-wheel-mouse-reporting` Risks) independently and *unprompted* discuss exactly this mechanism-targeting judgment inside their existing Decisions/Risks sections. A standing "Test precision" section would sit empty on the majority of changes that touch no test, inviting boilerplate.
   - The `xtty-openspec-critic` Pass-1 line is billed as a **heuristic → REVIEW** check (matching how `mechanism-neutrality` and `design↔requirements traceability` are already framed in that file), not as "mechanically checkable" — judging whether `design.md` names a claim/layer/driver-reach is a semantic prose read, exactly the class `AGENTS.md`'s own rule says the critic should flag for human review rather than treat as a hard gate.
   - *Alternative considered:* rely solely on `coherence-review`'s existing "a rule change propagates without editing the agent" deference mechanism (the agent already re-reads `AGENTS.md` fresh and flags un-checkable rules as REVIEW). Rejected as the *sole* mechanism — it would work, but gives a generic, unspecific flag; an explicit Pass-1 line gives a sharper, more useful one, which is why `harden-validator-delegation-trigger` similarly modified `test-validation`'s own requirement rather than relying only on deference.

**D3 — Rule wording must be symmetric, not just disclaimed.** A first draft explicitly stated "this is not an always-prefer-low-level-tests rule," but adversarial critique found the disclaimer insufficient: the cautionary example (`vim`/`less`/`htop`) is vivid and concrete, while the counter-example (a real program is *right* for an upstream claim, e.g. `testWheelScrollsRealMouseTrackingPager` proving routing) is short and abstract — a skimming reader retains the vivid lesson and over-applies it, converting *correctly-scoped* real-program tests into unnecessary synthetic ones. The rule text (below, and in the `AGENTS.md` edit) gives the "real program is right here" case equal concreteness and states explicitly that the failure mode runs in both directions: a driver — real program *or* hand-written synthetic sequence — can silently miss the intended mechanism if its escape-idiom doesn't reach it.

**Final rule text** (goes into `AGENTS.md`'s "Keeping a change coherent" walk-list verbatim, per D3's revision):

> **Test precision vs. the claim (design-time, Decisions).** When a change adds or modifies a test, `design.md`'s Decisions (or Risks/Trade-offs) MUST state (1) the exact claim the test proves, (2) the layer/mechanism that claim lives in, and (3) why the chosen driver reaches that layer. Then match the test's depth to the claim — symmetrically: an over-deep test is as wrong as a too-shallow one, and this is not a "prefer synthetic/low-level tests" rule. Decide by where the claim lives. A real end-to-end program is the right tool for a claim that lives upstream of any program-specific behavior — e.g. `testWheelScrollsRealMouseTrackingPager` drives real `less --mouse` to prove wheel routing (whether a mouse report reaches the program at all, decided before any redraw), so the program's own escape idiom is irrelevant and the real program is exactly right. A direct/synthetic driver is the right tool for a claim about one narrow internal code path a given program may or may not exercise — e.g. in `fix-scroll-reversal-redraw-corruption` only htop's ncurses hardware-scroll optimizer hits the buggy `cmdScrollDown` (`vim` uses already-guarded `IL`/`DL`, `less` a bare `RI` with no scroll region), so a real-pager test would pass green while proving nothing; the fix is instead proven by driving the exact `SU`/`SD`-inside-a-scroll-region sequence directly via `printf`. The trap runs both directions: a driver — real program or synthetic — can silently fail to exercise the intended mechanism because the escape-idiom choice (a real program's, or your own hand-written sequence's) may not match the path under test, and a program's idiom is outside this project's control. Worked exemplars already living in Decisions/Risks (no new machinery): `split-shell-dependent-testplan` D2 (assert forwarding fidelity per the shell's observed capability), `fix-scroll-wheel-mouse-reporting` Risks (assert the deterministic routing state-dump field, not a program's own scroll count).

## Risks / Trade-offs

- **[Risk] This rule is grounded in exactly one in-session near-miss plus a mostly-clean 7-file audit — thin evidence for new process, and in some tension with this project's own "add machinery only after friction recurs across several changes" principle (a Learned Refutation already in `AGENTS.md`, originally about not pre-building a speculative agent roster).** → Mitigation: scope this addition to match the tension — a one-line `AGENTS.md` bullet and one REVIEW-level (not blocking) heuristic line is far lighter-weight than a new agent or pipeline, and the honest framing (in this design and in the eventual research capture) states plainly that the rule has not yet proven itself against a second real case. If it never fires usefully on a future change, that is itself informative and this can be revisited.
- **[Risk] The audit that grounds "the codebase is currently clean" covered 7 of the AppUITests files, not all of them** (find-bar and multiplexing suites unaudited). → Accepted as a named, open gap (Non-Goals) — closing it is a separate, optional follow-up, not blocking this rule's addition.
- **[Risk] A REVIEW-level heuristic can be — and by design, sometimes should be — ignored by a human reviewer**, so this doesn't guarantee the mistake this session made can never recur. → Accepted; matching the existing `mechanism-neutrality`/`design↔requirements traceability` heuristics' own severity, which this change deliberately mirrors rather than over-claiming a stronger guarantee.

No migration. Two file edits (`AGENTS.md`, `.claude/agents/xtty-openspec-critic.md` + its `Definition version` bump), no code, no data. Rollback is a straight revert of both edits.
