## Context

Cross-review's Pass C currently pins "inline Opus" — reusing Pass A's exact checkpoint for the review's second Claude-family pass. Recent research (`research/03-analysis/cross-model-seat-assignment-research.md`) found this worth a bounded experiment: swap Pass C to Fable 5, a different Claude-family checkpoint, so the review's two Claude-family passes aren't literally the same model reviewing the same range twice. The spec already permits this — Pass C only has to share Pass A's model *family*, not its checkpoint, and the concrete pin is deliberately kept out of the requirement text: the established spec states the pin "SHALL live in the design document," and this document is that record — the operative copy of the pin lives in `cross-review.md` itself, the same way Pass B's `gpt-5.6-sol` pin already does. This design covers the mechanics of the swap and, more importantly, how to state and evaluate it honestly.

## Goals / Non-Goals

**Goals:**
- Swap Pass C's pinned model from Opus to Fable 5 in `.claude/commands/xtty/cross-review.md`.
- Prevent the swap from being misread as adding a third independent review family — only Pass B is cross-vendor.
- Establish a concrete, human-owned evaluation procedure so the experiment can actually be judged over time.

**Non-Goals:**
- Not touching Pass A, Pass B, the scope classifier, the digest tool, or the archive gate.
- Not building any new standing agent or automation to compute "disjointness" — that judgment stays human and manual.
- Not committing to keeping the Fable pin permanently; this is explicitly reversible pending evaluation.

## Decisions

1. **Pin Fable 5, not another Opus invocation or a rotating pin.** Rejected rotating between several Claude checkpoints per run (adds complexity with no clear evaluation win over a single fixed swap). Fable 5 is chosen because this repo has direct, recent evidence of a verified adversarial-critique capability floor: a separate, independent Fable-5 critique pass over the seat-assignment research investigation's own reasoning found concrete, verified defects (the evaluation-methodology correction and a conditional note on the author-family deferral, both captured in `cross-model-seat-assignment-research.md`) — grounded, specific findings against real repo state, not generic commentary. That evidence establishes a capability floor, not comparative value against Opus at this specific task — the checkpoint-diversity gain itself is the untested hypothesis this experiment exists to check. Keeping Opus (status quo) is rejected not because a diversity gain is known, but because it cannot generate the data needed to test whether one exists. This decision supersedes the archived `add-cross-model-design-review` design's D9 pin ("Passes A/C = Opus") for Pass C specifically. Correcting an earlier draft of this decision: the harness `Agent` tool used for Pass C's inline call exposes **no per-call effort parameter** (unlike a Workflow's `agent()`, which does) — so Pass C's effort is not invocation-pinnable at all, in contrast to archived D9's contrast between Pass C (previously assumed invocation-controlled) and Pass B (CLI-config-governed, no per-call flag). Pass C's effort is instead **inherited from the invoking session**; `cross-review.md`'s ledger-header contract now records it as reported/best-effort rather than a guaranteed pin, and recommends the human launching a run confirm their own session's reasoning effort is at a high/xhigh-equivalent tier first.

2. **ADDED requirement, not MODIFIED.** The existing "Authority-free cross-model review worker" requirement already accommodates a checkpoint swap without any edit — it explicitly keeps the concrete model pin out of the requirement text, and its "record the effective model of each soundness pass" language already covers whichever checkpoint runs, unchanged. Editing that requirement would mean pasting and re-threading a long, multi-scenario block for zero behavioral change to it. The two genuinely new expectations this change adds — documentation clarity about family-vs-checkpoint, and a human-only evaluation rule — are additive, so a new, narrowly-scoped requirement is cleaner and lower-risk than a large MODIFIED paste.

3. **Human-only evaluation, made explicitly normative.** This repo has a settled refutation: a model-authored artifact can never gate archive — the human is the gate. A mechanism where a model scores its own review pass's comparative value would repeat that mistake at smaller scale. Stating the evaluation rule as an explicit SHALL (rather than leaving it an unstated assumption) closes that off before anyone is tempted to build a "disjointness score" feature.

4. **No new tooling for the evaluation, for now.** Considered building a script that diffs Pass A's and Pass C's findings and reports overlap automatically. Rejected: building measurement tooling before a single run has happened is the same premature-machinery pattern the seat-assignment research already flagged and deferred for a different candidate (the author-family ledger field). If the pin proves valuable across several runs and a human keeps wanting the same comparison done by hand, that's the point to reconsider a tool — not before.

## Risks / Trade-offs

- [Risk] The swap adds nothing over Opus — Fable and Opus might simply agree on everything, or Fable might under-perform Opus at this specific adversarial-review task. → [Mitigation] The evaluation is explicitly scoped to "watch several runs," not "assume it works"; reverting is a small mechanical revert of the synced surfaces in one commit (see Migration Plan), and nothing else in the system depends on Pass C's specific checkpoint.
- [Risk] `.claude/commands/xtty/research.md` already records "Fable 5 is intentionally unused — not an analytical-reasoning tier" for its own tiering, which could read as inconsistent with pinning Fable here. → [Mitigation] That prior decision governs the research fan-out's tiering specifically (a different use case: ranked analytical tiers vs. review-diversity value); this change's ADDED requirement states that scoping directly, so a future reader sees the distinction instead of an apparent contradiction.
- [Risk] Once task 1.1 commits `.claude/commands/xtty/cross-review.md` — a path outside the docs/tracker allowlist — the reviewed range will classify **in scope** for cross-model review before archive (today, pre-implementation, the classifier reports out-of-scope: not yet knowable to be in scope, not a settled verdict). → [Mitigation] Expected and accounted for in `tasks.md` (the standard human-attestation cross-review task); the change is small enough that this is a light lift, not a blocker.
- [Risk] The first-ever Fable-pinned inline diversity pass run is `tasks.md` 2.2's own human-attestation cross-review of *this* change — a self-review under the just-edited protocol, since `cross-review.md` itself sits in the reviewed diff. → [Mitigation] Zero worker authority plus the human gate bound the harm; the human evaluator should bracket that first ledger (note it, don't count it) rather than treat it as the first data point in the multi-run disjointness evaluation.

## Migration Plan

No runtime migration — this is a documentation/prompt change across two files plus a spec delta merged at archive. Steps: edit `cross-review.md`'s Pass C mentions (the §2 description **and** the frontmatter `description` line) to pin Fable 5 and add the clarifying/evaluation language; update `AGENTS.md`'s "Cross-model design review" summary sentence to match; at archive, the spec delta merges into `openspec/specs/cross-model-review/spec.md`. Rollback reverts all synced surfaces together in one commit — `cross-review.md`'s pin (both mentions), the now-moot clarification/evaluation language, and `AGENTS.md`'s Pass-C sentence; the ADDED requirement can remain (it is honestly still true of "whichever checkpoint runs"), or be removed via a follow-up REMOVED delta if the experiment is abandoned outright.

## Open Questions

- How many cross-review runs constitute "enough" to judge the pin, given `/xtty:cross-review` never auto-fires and is human-launched only? **Resolved with a concrete trigger** (both external reviewers flagged the prior "left to human judgment, no threshold" answer as toothless — no owner/deadline meant the pin could coast unevaluated indefinitely): re-evaluate after the **3rd eligible non-self-review run** — **eligible** meaning any in-scope `/xtty:cross-review` run whose own reviewed diff does not itself modify Pass C's protocol in `cross-review.md` (excluding this change's own bootstrap dogfood run — see the self-review-confound risk above in Risks / Trade-offs) — **or** at the next `xtty:capture-research` pass touching cross-model review, whichever comes first — recorded as a dated one-line judgment appended to `cross-model-seat-assignment-research.md`'s open-questions list, giving the trigger a durable, git-visible home even without a persisted per-run ledger log.
- Should the human's ledger-disjointness judgment be recorded anywhere (a running log), or is an ephemeral per-run judgment sufficient? Resolved narrowly: the ADDED requirement accepts either a persisted per-run ledger (`cross-review-ledger.md`, already optional and gate-inert) or the human's own recorded per-run judgment, so the mandated multi-run comparison doesn't silently depend on unaided memory. Whether to build a running log beyond that is still left open — a natural follow-up for a later `xtty:capture-research` pass if the pin sticks around.
