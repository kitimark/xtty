## Context

`AGENTS.md` is 206 lines / 68,897 bytes. A prior diet (`slim-agents-context`, archived 2026-07-06) split narrative history out to `HISTORY.md` and cut the file 80.6KB→28.5KB, but the gain eroded within ~4-5 days (measured via `git show <sha>:AGENTS.md | wc -c` across every commit touching the file) at a rate that did not slow down versus before the diet. Two `/xtty:research` fan-outs (`research/03-analysis/agents-md-structural-best-practices.md` + its same-day addendum — 13 + 13 subagents, each pipeline ending in synthesis → adversarial critic → verify-by-effect) pinned down why: the "Shipped and archived" table's five phase rows (P0–P7) total ~1.2KB and stay bounded because each is edited only when a *phase* closes — a rare, terminal event. The sixth row, "Tooling," has no such closing phase (the project produces dev-workflow/CI/agent tooling continuously) and is edited on *every* archived tooling change, growing to 16,645 bytes (93% of the table, 24% of the whole file) as ~24 change narratives accreted into one cell. The Snapshot paragraph (5,768 bytes) carries the identical anti-pattern at smaller scale. Separately, "How to work here" carries four delegation-boundary bullets (`xtty-test-validator`, `xtty-ci-investigator`, `xtty-openspec-critic`, `/xtty:research`) that share an identical template — spawn scenarios / delegation-boundary verb pair / marker / deference chain / babysitter-or-not — repeated as four multi-paragraph essays (11,038 bytes) rather than one table.

The existing `research-capture` spec requirement already says a status-surface entry "SHALL NOT grow... beyond a bounded entry," but "bounded" was never defined precisely enough to prevent the Tooling row's growth while it remained nominally "one row." Verified against the repo: all ~24 of the Tooling row's change narratives already exist in `HISTORY.md` (the 5 oldest individually confirmed), so removing them from `AGENTS.md` is a pure deletion — no unique content at risk.

## Goals / Non-Goals

**Goals:**
- Restructure the Tooling row and Snapshot paragraph so they obey the shape the rest of the file's status surface already uses (bounded, one-line-per-unit with a detail pointer), and give "bounded" a precise operational definition (category-keyed) so the fix is checkable, not just aspirational prose.
- Tabularize the four near-identical delegation-boundary bullets in "How to work here" into one table, since they are structurally a table pretending to be four essays.
- Add a REVIEW-severity `xtty-openspec-critic` heuristic that can actually catch a future violation of the category-keyed bound, mirroring the established, lightweight pattern `harden-test-precision-vs-claim` already uses for an unrelated lesson.
- Ground every claim in what the two research fan-outs actually measured and adversarially verified — this design should not re-introduce a claim either fan-out's critique retired.

**Non-Goals:**
- **No mechanical CI byte/line-count gate.** Real precedent exists (`konflux-ci`, `tektoncd/catalog`, `cloudposse/atmos`, `homeassistant-ai/ha-mcp` all gate `AGENTS.md` size in CI with a plain `wc` shell step) but the research's adversarial critique found it disproportionate here: xtty pushes straight to `main` (no PR to hang a path-scoped gate on per the `xtty-push-to-main` convention), and a fixed ceiling on a file that legitimately carries durable content would either rarely fire or immediately red the repo. See D3.
- **No nesting** `AGENTS.md` into per-directory files. xtty is a single app plus one small SPM package (`XttyCore`), not a monorepo of differently-stacked subprojects — the bar every real nesting precedent (Airflow, Codex) clears. This was already the conclusion of the first research pass; restated here as a decision, not re-litigated.
- **No `HISTORY.md` edits.** It already holds the content this change removes from `AGENTS.md`'s status surface; it is not itself bounded (by design — the permanent archive is supposed to grow) and this change does not touch it.
- **No changes to the "Building" section's CI-history digest or `research/README.md`'s structure** — out of scope; a separate density concern not covered by this change's research.
- **No HTML-comment-wrapping of maintainer-only content.** Claude Code strips block-level HTML comments before context injection (a zero-token channel for human-only notes), surfaced by the first research pass as a real, usable mechanism — but nothing in this change's scope currently needs it (there's no maintainer-only content being carved out here, only narrative being routed to `HISTORY.md` instead). Left as a documented option for a future pass, not exercised now.

## Decisions

**D1 — Operationalize "bounded entry" as category-keyed, not change-keyed, for any perpetual (non-closing) status-surface row or paragraph.** This is the single load-bearing insight from the research: the phase rows stay bounded because they are edited on phase-closure (rare, terminal); the Open-changes table stays bounded because a row is removed at archive; the Tooling row and Snapshot paragraph grow because they are edited on *every qualifying change* with no terminal event. The fix generalizes past this one row — any future perpetual bucket in the guide should be category-keyed from the start. The `research-capture` spec delta states this precisely so a future coherence-review pass (D3 below) has a checkable definition rather than a vibe.
  - *Alternative considered:* import a release-cadence-anchored rotation pattern (towncrier/blurb fragment files, Keep a Changelog's Unreleased-section-frozen-at-release model, Kubernetes' PR-metadata extraction). Rejected — every one of these patterns is anchored to a periodic release cut that sweeps the accumulation zone; xtty has git tags (`v0.0.1`) but no release cadence, so importing any of them would recreate an unbounded bucket with added machinery (cpython's own `Misc/NEWS.d/next/` holds 431 unswept-at-any-given-moment fragments — bounded by its monthly release cadence, not by the mechanism itself; xtty has no equivalent cadence). xtty's actual cut point is its own per-change OpenSpec archive event, which already exists and already fires reliably — no import needed.
  - *Alternative considered:* a fixed numeric cap (e.g. "keep only the last 5 Tooling entries, drop older ones"). Rejected — this is change-keyed with a sliding window, not category-keyed; it still requires an edit on every qualifying change (removing the oldest, adding the newest) and doesn't eliminate the churn, just bounds its size. Category-keying eliminates per-change edits to the row entirely for an already-represented category.

**D2 — Bundle the Tooling row, Snapshot paragraph, and "How to work here" tabularization into one change**, mirroring `slim-agents-context`'s precedent of bundling three unrelated blobs (Current-status paragraph, OpenSpec-workflow changelog tail, Building CI-history) into a single change.
  - *Alternative considered:* split into two changes (rotation/category-keying vs. delegation-bullet tabularization), floated during the preceding explore-mode session. Rejected on reflection — both fixes land in the same file in the same editorial pass, neither has independent risk that benefits from separate archival, and splitting would double the coherence-review + archive-ritual overhead for no isolation benefit. The two research fan-outs that grounded this change both treated the Tooling-row/Snapshot fix as the primary subject; the delegation-bullet tabularization is a smaller, well-understood, non-research-requiring formatting fix riding along.

**D3 — Enforcement: land the `xtty-openspec-critic` heuristic as the proportionate primary mechanism; explicitly do not pair it with a mechanical CI gate this round, and do not claim it is proven sufficient.** The two research fan-outs' adversarial critiques appeared to disagree but actually narrow the same option space from two directions: the first critic rejected a *mandatory CI ratchet* as disproportionate for a push-to-main repo (no PR to trigger it; a hard ceiling would either rarely fire or immediately red a file with legitimate content); the second critic rejected *overselling* the critic heuristic as something that "makes the sweep durable" — xtty already has a *written* rule forbidding narrative paragraphs in the status surface, and it is being violated right now, and the in-flight `harden-test-precision-vs-claim` change's own Risks section explicitly states a REVIEW-level heuristic "can be, and by design, sometimes should be, ignored by a human reviewer." Both are correct. The resolution: land the heuristic (cheap, matches existing tooling, gives a crisp checkable signal per D1's definition) as the primary mechanism, but treat its sufficiency as an open, measured question rather than a settled one — track the Tooling row's (and Snapshot paragraph's) byte size after each of the next several archives; if it climbs materially past a category-keyed one-liner, that is the signal to revisit a non-blocking byte/char warning (real precedent found: `homeassistant-ai/ha-mcp`'s 40k-char warning, explicitly tied to Claude Code startup performance — a rationale xtty has already measured in `agents-md-context-budget.md`), not to silently let the row regrow a third time.
  - *Alternative considered:* add the non-blocking byte-warning CI step now, alongside the heuristic, as a belt-and-suspenders pair. Rejected for this change — it adds a CI step for a not-yet-demonstrated failure mode (the heuristic hasn't had a chance to work or fail yet), and the research explicitly left this as an option for "the future proposal to decide" once informed by the heuristic's actual track record. Revisit if the re-verification in Migration Plan below shows regrowth.

**D4 — This change's `coherence-review` delta will collide with `harden-test-precision-vs-claim`'s in-flight delta on the same requirement ("Committed coherence-review agent tooling").** Both changes are open simultaneously and both add a heuristic sentence + scenario to the same requirement block. This is exactly the "shared-requirement collision" scenario `coherence-review`'s own spec already anticipates and instructs the coherence-review agent to surface (it "constrains the archive/merge order," not that it's forbidden). Whichever change archives second will need to hand-merge both heuristic additions into one requirement block per the project's own "finish the merge by hand" archive step — flagged here explicitly so neither the coherence-review pass nor a future reader is surprised by it.
  - *Alternative considered:* wait for `harden-test-precision-vs-claim` to archive first to avoid the collision. Rejected — it is a docs-only, no-code, independent change with no actual coupling beyond touching the same file region; sequencing around it would add delay for no correctness benefit, and the collision is cheap to resolve by hand at whichever archive happens second.

## Risks / Trade-offs

- **[Risk] The category-keyed Tooling-row rewrite could under-summarize** — collapsing ~24 distinct tooling changes into one line risks losing orientation value for a reader scanning `AGENTS.md` who wants to know "what tooling changes have landed" without opening `HISTORY.md`. → Mitigation: the one-line summary names the *categories* (CI, dev-workflow agents, install/signing, test-image/VM, launchers), not just "see HISTORY.md" — enough to know what exists and where to look, matching how the phase rows already summarize multi-item scopes in one clause.
- **[Risk] The critic heuristic's sufficiency is genuinely unproven** (see D3) — this change could ship and the row could still regrow if the heuristic is ignored or the reconcile step simply isn't run carefully. → Mitigation: explicitly tracked as an open, measured question (Migration Plan), not silently assumed; a recurrence is informative (as `harden-test-precision-vs-claim`'s own Risks section already accepts for its own heuristic) and would justify revisiting D3's rejected CI-gate alternative, not repeating the same unenforced-rule mistake a third time.
- **[Risk] Shared-requirement collision with `harden-test-precision-vs-claim`** (D4) adds a small amount of manual-merge care at whichever change archives second. → Accepted; cheap, and the coherence-review agent is specifically built to surface exactly this kind of collision so it isn't missed.

## Migration Plan

Docs- and agent-tooling-only; no code, no data, no build changes. Steps: (1) rewrite the Tooling row, Snapshot paragraph, and "How to work here" delegation bullets in `AGENTS.md` in place; (2) add the new `xtty-openspec-critic` Pass-1 heuristic line + bump its `Definition version` stamp; (3) `openspec archive` merges the two spec deltas into `openspec/specs/research-capture/spec.md` and `openspec/specs/coherence-review/spec.md` (hand-merging the coherence-review requirement against whatever `harden-test-precision-vs-claim` has already merged, per D4, if it archived first). Rollback is a straight revert of the `AGENTS.md` and agent-file edits; the spec deltas revert with `openspec archive`'s own history if needed. Re-verification: `wc -c AGENTS.md` should drop sharply (the Tooling row alone recovers ~16.5KB); re-run `grep -n '| Tooling |' AGENTS.md | wc -c` after each of the next several archived changes and confirm it stays near-constant rather than climbing — this is the actual test of D3's heuristic-sufficiency question, not a one-time measurement.
