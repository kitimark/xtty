## ADDED Requirements

### Requirement: Committed design base derived from shipped source

The project SHALL maintain a version-controlled Open Design design-system package describing xtty's visual language. Every value in that package SHALL be classified by provenance as one of: **measured** (the literal appears in xtty's own source, cited to `path:line`), **platform** (resolved by AppKit/SwiftUI, which xtty does not set), or **derived** (no xtty equivalent exists; a judgement call filling a required slot). A derived or platform value SHALL NOT be presented as a fact about xtty.

The package SHALL bind every token name required by the design tool's token schema, and any value the project needs beyond that schema SHALL carry a project-specific prefix so its non-standard status is evident from the name alone.

The package SHALL record that it cannot be regenerated by any importer — the design tool's importers scan web-stack files only and would extract nothing from a Swift tree — so that a future contributor does not attempt to "refresh" it with a tool that would overwrite the authored prose.

#### Scenario: Every required schema token is bound

- **WHEN** the design base is validated against the design tool's token schema
- **THEN** every token name the schema requires is present in the package
- **AND** no unprefixed token name is present that the schema does not define

#### Scenario: A value with no source in xtty is labelled, not cited

- **WHEN** the design base states a value that xtty's source does not contain
- **THEN** that value is marked as platform-resolved or derived
- **AND** it carries no `path:line` citation implying xtty authored it

#### Scenario: Regeneration is warned against at the point of risk

- **WHEN** a contributor reads the design base or the linkage tooling
- **THEN** both state that the tool's folder-import path regenerates the design document from a source scan and would destroy the authored prose

### Requirement: Mockups classify as baseline or proposal

Every mockup SHALL declare, in its filename, whether it reproduces UI that ships today (**baseline**) or proposes UI that does not (**proposal**). A baseline SHALL cite the source that implements the surface it draws, and SHALL only be edited to improve fidelity to that source. A proposal SHALL be visually distinguishable as unshipped when opened.

A proposal for a surface with no corresponding baseline SHALL be treated as describing a feature xtty does not have, and SHALL say so in the rendered page — not only in its filename.

#### Scenario: A baseline is identifiable and traceable

- **WHEN** a contributor opens a mockup named as a baseline
- **THEN** it states the source files and lines implementing the surface it reproduces
- **AND** its content reproduces what ships rather than proposing changes

#### Scenario: A proposal for a non-existent surface is unmistakable

- **WHEN** a mockup proposes a surface that has no baseline counterpart
- **THEN** the rendered page itself declares that no such surface exists in xtty today

#### Scenario: Fidelity edits and design changes do not mix

- **WHEN** a change to a baseline mockup is proposed
- **THEN** it is accepted only if it moves the mockup closer to the shipped source
- **AND** any change to the design itself is made as a proposal variant instead

### Requirement: Committed content is separated from machine-local residue

The design folder SHALL carry ignore rules that exclude the design tool's regenerable, machine-local residue while keeping agent-produced content version-controlled. The rules SHALL be documented per entry with the reason for each exclusion, and SHALL be placed outside the design agent's own working directory so that modifying them is a reviewable event rather than a silent one.

Anything not explicitly classified SHALL remain visible to version control on purpose, so that an unrecognized file surfaces for investigation instead of disappearing.

#### Scenario: Regenerable residue is excluded

- **WHEN** the design agent stages its per-turn working files into the project directory
- **THEN** those files are excluded from version control
- **AND** the exclusion entry records why the file is regenerable

#### Scenario: An unrecognized file surfaces rather than hiding

- **WHEN** the design tool writes a file the ignore rules do not name
- **THEN** that file appears in version-control status for investigation

#### Scenario: A hidden marker is checked explicitly

- **WHEN** an ignore rule hides a file whose mere existence signals a broken state
- **THEN** the post-run checklist tests for that file's existence directly, since status output can no longer reveal it

### Requirement: The design base reaches the agent only when the package is selected

The project SHALL record that pasting the design base into the design agent's prompt requires the package to be **registered, published, and selected** for the project, and that a package failing any of these conditions produces output that can still look correct by coincidence. The recorded verification SHALL therefore be **by effect** — confirming a value unique to the committed design base appears in generated output — and SHALL NOT rely solely on reading configuration state.

#### Scenario: Linkage is proven by generated output

- **WHEN** a contributor verifies that the design base is reaching the agent
- **THEN** the check confirms a value unique to the committed base appears in freshly generated output
- **AND** a configuration read alone is treated as a precondition, not as proof

#### Scenario: Coincidental fidelity is not accepted as success

- **WHEN** generated output matches xtty's appearance but the package is not selected for the project
- **THEN** the linkage is treated as unverified

### Requirement: The design base's update lifecycle is recorded

The project SHALL document which parts of the design base propagate to the design tool automatically and which do not, including the remediation for any part that does not. Where a stale state is reachable without any visible signal, that silent failure mode SHALL be stated explicitly.

#### Scenario: A part that does not propagate is documented with its remedy

- **WHEN** a contributor edits a part of the design base that the tool caches rather than re-reads
- **THEN** the documented lifecycle tells them the cache must be cleared and how
- **AND** it states that skipping this yields fresh values with stale prose, with no error shown

### Requirement: Safety posture for an unsandboxed design agent

The project SHALL record that the design agent runs without permission prompts and without an OS-level sandbox, so scoping it to a dedicated folder bounds blast radius without enforcing a boundary. The recorded posture SHALL require a clean, pushed working tree before each run; a repository-wide review of working-tree and history state after each run; staging by explicit path only; and content telemetry disabled before any run that reads private source.

Where a failure mode has no rollback, the posture SHALL identify it as prevention-only rather than implying it can be repaired after the fact.

#### Scenario: Folder scope is not presented as enforcement

- **WHEN** a contributor reads the recorded safety posture
- **THEN** it states that the folder boundary is not enforced and has been observed to be crossed

#### Scenario: Post-run review covers the whole repository

- **WHEN** a design agent run completes
- **THEN** the checklist reviews repository-wide status, differences, and history state — not only the project folder

#### Scenario: Unrecoverable failure modes are named as prevention-only

- **WHEN** the posture describes a failure mode with no rollback
- **THEN** it says so explicitly rather than describing a remediation that does not exist
